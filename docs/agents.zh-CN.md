# Keyhook-agent — Agent 目录与人机边界（v0.1）

[`spec.zh-CN.md`](spec.zh-CN.md) 的配套文档。spec 详细定义了维修 agent；本文把它放进一个 AI 原生物业管理
平台所需的完整 agent 版图中，并界定 agent 与人的分工边界。

> 状态：产品分析。标注 **（提议）** 的行尚未确认为业务规则，实现前需确认。新西兰法规细节在依赖前
> 必须对照 Tenancy Services 和《Residential Tenancies Act》核实。本文是产品策略，不构成法律意见。
> 以英文版 [`agents.md`](agents.md) 为准。

## 1. 这个岗位真正要的是什么

| 招聘原文信号 | 对产品的含义 |
|---|---|
| "so our customers can focus on adding tremendous value to landlords and tenants" | 客户是物业经理（PM）。目标是消除 PM 的琐事，**不是取代 PM** |
| "Escalate when a person needs to be involved" | 有边界的自治是明确要求，不是全自动 |
| "Keep going until the job is done" | 价值在于闭环：跟进、催办、确认、关单——正是人最容易漏的环节 |
| "real production software; not demos, chatbots" | 标准是可靠性、评测、审计、安全 |
| "Make Keyhook increasingly capable of doing the work itself" | 两层含义：产品替客户干活，**同时**公司自身的工程也要自动化（测试、安全、开发工具） |
| "four people, three systems and nine manual steps" | 价值衡量方式：消掉多少人、多少系统切换、多少手工步骤 |
| 直接汇报给 CEO；一次招 3 人 | 公司级战略，不是边缘试验 |

**商业逻辑。** 物业管理公司的主要成本是人力。如果一个 PM 从管理约 100 套房提升到 200–300 套，
产品卖的就是"少招人"而不是软件席位。目标是减少单位工作的人工*劳动*，而不是去掉人：PM 的角色从
执行者转变为监督者、例外处理者和关系维护者。

## 2. 行业需求（新西兰住宅物业管理）

一套房在一个租约周期内的生命周期：

```
招租 → 申请/筛选 → 签约/押金 → 入住检查
→ 日常（租金、维修、巡检、沟通）
→ 续约/调租 → 退租检查 → 押金退还/争议 → 重新招租
```

痛点：
1. **量大且重复**——消息、提醒、催办、排期，占据 PM 大部分时间。
2. **合规有硬时限**——如向 Tenancy Services 登记押金、进屋/巡检前的书面通知、调租的通知期与频率限制、
   Healthy Homes 标准。错过会面临罚款或 Tenancy Tribunal 风险。*（具体天数与规则：使用前需核实。）*
3. **多方协调**——租客、房东、师傅、PM 之间来回传话。

## 3. Agent 如何分类

**3.1 教科书划分（Russell & Norvig）**——按智能程度：简单反射型、基于模型的反射型、基于目标型、
基于效用型、学习型。是理论框架，不是产品框架。

**3.2 Workflow 与 Agent（工程视角）**
- *Workflow*：步骤由代码定义，LLM 在某一步内做判断（分类、抽取、起草）。
- *Agent*：由 LLM 决定下一步做什么、调用哪个工具。
- 大多数生产级"agent"应当是 workflow 加局部 LLM 决策。Keyhook-agent 正是如此：状态机掌控流程，
  LLM 只在步骤内决策（CLAUDE.md 规则 1）。自主度越高，越难测试和审计。

**3.3 多 agent 系统中的角色**——路由者（router）、编排者（orchestrator）、专家执行者（worker）、
校验者（critic/verifier）。

**3.4 本项目采用的产品分类：触发方式 × 自主度**

| 触发方式 \ 自主度 | 只建议 | 执行需审批 | 自主执行 |
|---|---|---|---|
| **被动响应**（事件：收到消息） | | | |
| **主动巡查**（定时：扫描隐患） | | | |
| **人工调用**（PM 发起："帮我起草报告"） | | | |

每个 agent 先落到格子里，再细化到**每个动作**：同一个 agent 内，"发消息"可以自主，"花钱"需要审批。
这就是工具权限分级 `read | auto | approval`（spec §8）的由来。

## 4. Agent 目录

### 4.1 面向客户（产品）

| Agent | 触发 | 职责 | JD 点名？ | 项目状态 |
|---|---|---|---|---|
| **收件分诊 / 路由** | 被动 | 对所有进站消息分类，路由给对应 agent 或 PM | 隐含 | 后续 |
| **维修** | 被动 | 报修 → 分诊 → 找师傅 → 报价 → 审批 → 排期 → 确认 → 关单 | ✅ | **v1（spec）** |
| **欠租** | 被动 + 主动 | 逾期提醒、还款计划、起草正式通知 | ✅ | **已完成（M9）** |
| **租赁申请** | 被动 | 收集并核验材料、生成对比摘要 | ✅ | 不在范围内 |
| **巡检** | 主动 | 排期、发法定通知、根据照片/笔记起草报告、生成后续维修单 | ✅ | 不在范围内 |
| **租约生命周期** | 主动 | 续约、调租、押金登记、退租流程 | ✅ | 不在范围内 |
| **资产组合监控** | 主动 | 发现重复故障、合规缺口、临近的截止日期 | ✅（"before the PM knows"） | **已完成（M8）**：重复故障；合规检查需要数据源 |
| **房东沟通 / 报告** | 人工调用 + 定时 | 月报、审批请求、费用解释 | 隐含 | 后续 |

### 4.2 面向内部（工程）

| Agent | 职责 | JD 点名？ |
|---|---|---|
| **QA / 探索式测试** | 在客户之前发现 bug | ✅ |
| **安全与性能测试** | 定期扫描、压测、回归对比 | ✅ |
| **故障调查** | 根据报错/日志定位原因，提出或提交修复 | ✅ |
| **开发效率工具** | 代码审查、迁移、文档 | ✅ |

在本项目中，评测体系（spec §10）和 CI 是内部工程方向的展示点。

### 4.3 共享平台才是核心资产

所有 agent 共用同一套基础设施：带权限分级的工具、状态机、审批记录、审计日志、幂等性、评测、升级机制。
**Agent 很薄，平台很厚。** 第二、第三个 agent 的成本取决于平台复用程度——这正是 spec §4 把欠租列为
"复用同一套工具/评测基础设施的第二个工作流"的原因。

## 5. 人机边界

### 5.1 四个判断维度

1. **可逆性**——发错一条提醒可以补救；发错一份终止租约通知无法挽回。
2. **影响面**——涉及钱、法律后果、人身安全、住房稳定 → 更谨慎。
3. **置信度**——信息缺失、情况新奇或模型置信度低 → 交给人。
4. **问责**——法律责任在房东/PM 身上，agent 无法承担。

### 5.2 自主度矩阵

| 领域 | Agent 自主执行 | Agent 准备，人批准 | 只能由人 |
|---|---|---|---|
| 维修 | 分诊、追问细节、找师傅、要报价、排期、催办、确认完工 | 超出 PM 有效额度的花费；责任不明（可能是租客造成的损坏） | 紧急情况的现场决策（agent 立即通知）；与受伤或愤怒租客的沟通 |
| 欠租 **（M9 已实现；阈值为提议值）** | 友好提醒、记录还款承诺、跟踪还款计划 | 正式通知（agent 起草） | 申请 Tenancy Tribunal；困难户与家暴相关情况 |
| 租赁申请 **（提议）** | 收集材料、检查完整性、生成对比 | 推荐名单 | **最终选定租客**——《人权法》反歧视与《隐私法》风险；模型永不拍板 |
| 巡检 **（提议）** | 排期、发通知、起草报告、生成维修单 | 发给房东的最终报告 | 租客过错认定；押金扣除 |
| 租约生命周期 **（提议）** | 到期提醒、押金登记、文书准备 | 调租金额；续约条款 | 终止租约；押金争议 |
| 资产监控 **（提议）** | 发现问题、生成建议 | 是否立项处理 | 重大资本性建议（如更换整套系统） |
| 工程 | 跑测试、写调查报告、开 PR | 合并 PR | 生产变更的最终放行 |

维修一行与 spec §5–§8 及 `decisions.zh-CN.md` 中的审批策略一致
（≤ PM 有效额度自动通过；≤ 业主额度需 PM 审批；超出则升级）。

### 5.3 升级本身就是产品界面

升级绝不只是一句"请联系人工"。每次升级都必须附带：摘要、已完成的操作、建议的下一步、证据链接
（spec §7）。目标：PM 用约 30 秒做决定，而不是花 10 分钟重新调查。

## 6. 对本项目的启示

1. **把维修做深**——它正是"四个人、三个系统、九个步骤"的典型场景。
2. **增加一个小型主动 agent**——资产组合监控：发现种子数据中 Newtown 房产一年三次热水故障，并建议更换。
   成本低，直接回应"before the PM knows"。
3. **把评测作为核心卖点**——它对应"check their own work"和"systems that test, monitor and improve
   themselves"，也是区分生产软件与 demo 的关键。
4. **演示叙事（2 分钟）**——一条租客消息 → agent 推进工单 → 超额花费升级给 PM → 一键批准 → 闭环 →
   展示审计日志与评测分数。
5. **补齐 Keyhook 现有平台旁边的缺口**（2026-10-18，`docs/keyhook-fit.zh-CN.md`）——租客媒体分析、报价变更、发票核对、
   巡检发现 → 工单、业主与租客节点通知、资产组合监控、欠租（spec §12，里程碑 M6–M9）。房源、筛查、电子签名和财务仍属于
   Keyhook 平台。
