# AI 工程扩展知识点（面试补充）

> 配套：[速学版](interview-quickstart.zh-CN.md) · [详细版](interview-guide.zh-CN.md)。
> 本项目刻意**没用** LangGraph、向量库、RAG——面试时讲清"是什么 + 为什么没用 + 什么时候会用"，这是加分项。

每个知识点的格式：
**是什么** → **怎么工作** → **一句话答法** → **和本项目的关系** → **可能的追问**

优先级：⭐⭐⭐ 必须会 · ⭐⭐ 应该懂 · ⭐ 了解即可

## 1. AI Agent 基础 ⭐⭐⭐

**是什么**：LLM + 工具 + 循环。模型不只是回答，还能调用工具、看结果、继续行动，直到完成任务。

**怎么工作（ReAct 模式）**：
```
思考（我该做什么）→ 行动（调用工具）→ 观察（工具返回结果）→ 再思考 …… → 给出最终答案
```

**Workflow vs Agent**（Anthropic《Building Effective Agents》的核心区分）：
| | Workflow | Agent |
|---|---|---|
| 谁决定下一步 | 代码 | 模型 |
| 可预测性 | 高 | 低 |
| 适合 | 固定业务流程 | 开放式任务（写代码、做研究） |

**常见模式**：
- **Prompt 链**：一步输出作为下一步输入
- **路由**：先分类，再交给不同处理器
- **并行**：多个调用同时做，再汇总
- **编排器-工人**：一个模型拆任务，多个模型执行
- **评估-优化**：一个生成，一个打分，循环改进

**一句话答法**：
> "Agent 就是 LLM 在循环里使用工具。但生产环境应该从最简单的方案开始，能用 workflow 就不用全自主 agent，因为越自主越难测试和审计。"

**和本项目的关系**：本项目是 **workflow + 一个有界工具循环**。状态机是 workflow 骨架；只有 TRIAGED 状态里模型能自己选工具（≤ 8 轮，结束后自检）。还用到了**路由**（收件箱路由：房租还是维修）和**评估-优化**（红队生成 + 评委打分）。

**可能的追问**：
- *"Agent 最大的风险是什么？"* → 不可预测、难测试、成本不可控、可能执行危险动作。对策：限制轮数、工具白名单、权限分级、自检、人工审批。
- *"怎么防止 agent 死循环？"* → 最大轮数（本项目 8 轮、`advanceJob` 最多 6 步）+ 超时 + 成本上限。

## 2. Tool Use / Function Calling ⭐⭐⭐

**是什么**：让模型"调用函数"。模型不直接执行，只输出**工具名 + JSON 参数**，由你的代码执行。

**怎么工作**：
```
1. 你把工具定义（名字、描述、JSON Schema 参数）发给模型
2. 模型返回：{ tool: "search_tradies", input: { trade: "plumbing", suburb: "Newtown" } }
3. 你的代码执行，把结果发回给模型
4. 模型继续：再调工具，或给出最终回复
```

**设计好工具的要点**：
- 描述写清楚"什么时候用、什么时候别用"
- 参数要有严格校验（类型、范围、枚举）
- 出错时返回**结构化错误**，让模型能自己改正
- 工具数量少而精，太多会让模型选错

**一句话答法**：
> "模型只负责'说要调什么'，执行权永远在代码。所以校验、权限、幂等、审计都应该放在执行那一层。"

**和本项目的关系**：`executeTool` 网关——Zod 校验 → 权限级别（read/auto/approval）→ 幂等 key → 审计日志。`approval` 级工具（批钱）**根本不给模型看**。

**可能的追问**：
- *"模型编造参数怎么办？"* → Schema 校验 + 业务校验（比如师傅 id 必须来自 `search_tradies` 的结果）。
- *"工具调用失败怎么办？"* → 返回结构化错误让模型重试；超过次数或是系统错误就升级给人。
- *"结构化输出和 tool use 有什么区别？"* → 结构化输出是让模型按 schema 返回数据，由代码决定做什么；tool use 是模型决定调哪个工具。本项目大多数步骤用结构化输出，更可控。

## 3. RAG（检索增强生成）⭐⭐⭐

**是什么**：Retrieval-Augmented Generation。模型不知道你的私有知识，那就**先检索相关资料，再塞进 prompt** 让它回答。

**怎么工作**：
```
离线（建索引）：
  文档 → 切块（chunk，如每块 500 字）→ embedding 转成向量 → 存入向量库

在线（回答问题）：
  用户问题 → embedding → 在向量库找最相似的 top-k 块 → 拼进 prompt → 模型生成答案（附引用）
```

**进阶要点**（面试加分）：
| 问题 | 解决方法 |
|---|---|
| 切块太大/太小 | 按语义/段落切，块之间留重叠 |
| 纯向量检索漏关键词（如型号、编号） | **混合检索**：BM25 关键词 + 向量，再融合 |
| 检索结果不够准 | **重排序（Rerank）**：用 rerank 模型对 top-50 重新排序取 top-5 |
| 模型编造 | 要求只依据检索内容回答，并给出引用；找不到就说不知道 |
| 怎么评测 | 检索层：召回率/命中率；生成层：忠实度（是否基于资料）、相关性 |

**RAG vs 长上下文**：模型上下文越来越长，但 RAG 仍然更便宜、更快、能更新、能做权限过滤。

**一句话答法**：
> "RAG 解决的是'模型不知道私有或最新知识'。效果好坏主要取决于检索质量——切块、混合检索、重排序——而不是生成那一步。"

**和本项目的关系**：
- **为什么没用**：系统需要的数据都是**结构化**的（工单、物业、租约、师傅），用 SQL 精确查比语义检索更准确。没有"从大量非结构化文档里找答案"的需求。
- **什么时候会用**：
  1. 租客问租房法规问题（检索 Tenancy Services / Healthy Homes 文档）
  2. 在历史工单里找"类似故障是怎么修的"
  3. 物业经理问"这个房子过去两年出过什么问题"

**可能的追问**：
- *"RAG 检索不到相关内容怎么办？"* → 设相似度阈值，低于阈值就回答"不知道"或升级给人。
- *"多租户 RAG 怎么防止数据泄露？"* → 检索时按 organization_id 过滤（metadata filter），或用 pgvector + RLS。

## 4. Embedding 与向量数据库 ⭐⭐⭐

**是什么**：
- **Embedding**：把文本变成一串数字（向量，比如 1024 维）。**意思相近的文本，向量距离也近**。
  "没热水" 和 "热水器坏了" 的向量很接近，虽然字不一样。
- **向量数据库**：专门存向量、能快速找"最相似的 N 个"的数据库。

**怎么工作**：
- 相似度：常用**余弦相似度**（看方向是否一致）
- 数据量大时不能一个个比，用**近似最近邻（ANN）索引**，最常见的是 **HNSW**（分层图结构，牺牲一点准确度换速度）

**常见选择**：
| 方案 | 特点 |
|---|---|
| **pgvector** | Postgres 插件，和业务数据在一起，能用事务和 RLS |
| Pinecone | 全托管云服务，省心 |
| Qdrant / Weaviate / Milvus | 开源专用向量库，规模大时性能好 |
| Elasticsearch / OpenSearch | 已有搜索系统时，关键词 + 向量一起做 |

**一句话答法**：
> "Embedding 让'语义相似'变成可计算的距离。中小规模我首选 pgvector，不用多维护一个系统，还能沿用 Postgres 的事务和行级权限。"

**和本项目的关系**：没用。如果要加，选 **pgvector**——本项目已经是 Postgres + RLS 多租户，向量表加 `organization_id` 后天然隔离，不会跨公司泄露。

**可能的追问**：
- *"什么时候需要独立的向量库？"* → 向量数量上亿、检索 QPS 很高、需要专门调优时。
- *"embedding 模型换了怎么办？"* → 不同模型的向量不兼容，必须全部重新生成。

## 5. LangChain / LangGraph ⭐⭐

**是什么**：
- **LangChain**：LLM 应用的组件库——模型调用、prompt 模板、检索器、文档加载器等，像"乐高积木"。
- **LangGraph**：用**图**来编排 agent 的框架。

**LangGraph 核心概念**：
| 概念 | 意思 |
|---|---|
| State | 在节点之间传递的共享状态（一个对象） |
| Node | 一个步骤（调模型、调工具、跑代码） |
| Edge | 节点之间的连接；**条件边**根据状态决定去哪 |
| Checkpointer | 每一步后保存状态，可以中断后恢复、回放 |
| `interrupt()` | 暂停等待人工输入（人在回路） |

**一句话答法**：
> "LangGraph 适合需要灵活编排、多 agent 协作、快速原型的场景。但如果流程固定、要等好几天、状态必须和业务数据一致，我更倾向用状态机 + 持久化执行引擎。"

**和本项目的关系**（重点准备！文档 `docs/agent-design.md` §12 有原文）：
- 没用的理由：
  1. 流程是**固定业务流程**，不需要运行时编排
  2. 状态应该放在**业务表**里，checkpoint 会变成"第二个真相来源"
  3. 等几天、定时、重试是**持久化执行**问题，用 Inngest 解决
  4. 审批要跨好几天、多个经理、需要审计 → 用审批**记录**而不是 `interrupt()`
- 迁移接缝：如果以后要用，任何图节点都可以调用 `executeTool`，权限、幂等、审计不变。

**可能的追问**：
- *"LangGraph 的 checkpoint 和你的数据库状态有什么区别？"* → checkpoint 是框架内部的执行快照；本项目的状态就是业务数据本身，后台、审计、agent 读的是同一份。

**建议**：花半天照官方教程写一个"带人工审批的小 agent"，被问到时能讲具体体验。

## 6. Prompt Engineering 与 Context Engineering ⭐⭐

**Prompt Engineering 要点**：
- **系统提示词**：定义角色、规则、边界
- **Few-shot**：给几个示例，让模型模仿格式
- **结构化输出**：用 JSON Schema 约束返回格式
- **思维链**：让模型先推理再回答（复杂判断时）
- **XML 标签分隔**：区分指令和数据（本项目的 `<untrusted_message>`）

**Context Engineering（上下文工程）**——比 prompt 更重要的新概念：
> 决定"每一步给模型看什么信息"。信息太少会出错，太多会分散注意力、变慢变贵。

**Prompt Caching（提示词缓存）**：
- 把 prompt 中**不变的前缀**（系统提示词、工具定义）缓存起来，后续调用只算变化部分
- 省钱（缓存命中部分便宜很多）、更快

**一句话答法**：
> "Prompt 写得好只是基础，更关键的是上下文工程——每一步只给模型完成这一步所需的信息。"

**和本项目的关系**：
- 每一步**从数据库重建上下文**（工单、物业、租约、最近 12 条消息、历史工单），而不是不断累积聊天记录
- 撰写消息时只给一份**事实清单**，防止模型编造"已安排好"
- 稳定前缀做了 prompt caching，缓存命中在 trace 页面可见

## 7. MCP（Model Context Protocol）⭐⭐

**是什么**：Anthropic 推出的开放协议，**统一 agent 接入工具和数据的方式**。类比"AI 的 USB-C 接口"。

**怎么工作**：
- **MCP Server**：提供工具（tools）、资源（resources）、提示模板（prompts）
- **MCP Client**：在 agent 里，连接 server 并使用它的能力
- 写一次 server，任何支持 MCP 的 agent（Claude、IDE、其他应用）都能用

**一句话答法**：
> "MCP 把工具标准化，一个工具写一次就能被不同 agent 复用，不用每个框架重新适配。"

**和本项目的关系**：下一步计划——把 `executeTool` 网关暴露成 MCP server，其他 agent（包括 Keyhook 自己的）也能用这些工具，**且保留同样的权限、幂等和审计**。

## 8. LLM 评测（Evals）⭐⭐⭐

**为什么重要**：LLM 输出不确定，改一个 prompt 可能修好一处、搞坏三处。没有评测就是"凭感觉上线"。

**方法**：
| 方法 | 适合 |
|---|---|
| 规则/断言 | 能精确判断的：格式、状态、是否调了某个工具 |
| 标准答案集（Golden set） | 分类准确率等 |
| **LLM-as-judge** | 难用规则判断的：语气、是否有帮助、是否编造 |
| 人工审核 | 抽查、校准评委 |
| 红队 | 主动找漏洞（注入、越权） |

**工具**：promptfoo、LangSmith、Langfuse、Braintrust、OpenAI Evals。

**一句话答法**：
> "评测是 LLM 应用的单元测试。我会在每次改 prompt 或换模型时跑评测、对比分数，并把线上发现的错误变成新的测试用例。"

**和本项目的关系**（你的强项，重点讲）：
- 84 个 YAML 场景，跑真模型；指标：紧急度/工种准确率、升级精确率/召回率、最终状态、**升级原因**
- **禁止动作必须为 0**
- 红队自动生成攻击用例 + 评委打分
- 经理纠错 → 自动收割成草稿场景 → 人工审核 → 加入评测集
- 用评测数据选模型：Kimi 升级精确率 0.88 vs Claude 1.0

**可能的追问**：
- *"LLM-as-judge 可靠吗？"* → 需要人工校准；评委要给明确评分标准；本项目的评委还能看到系统的工具执行结果，不只看文本。

## 9. 多 Agent 系统 ⭐

**是什么**：多个 agent 分工协作，比如一个规划、几个执行、一个审查。

**常见框架**：CrewAI（角色扮演式团队）、AutoGen（对话式协作）、OpenAI Agents SDK（handoff 交接）、Claude Agent SDK。

**一句话答法**：
> "多 agent 能分工，但也带来协调成本、更多失败点和更难调试。只有在任务真正需要不同专长或并行时才用。"

**和本项目的关系**：多个 agent（维修、欠租、组合监控、运维分析）**共享一个平台**（工具网关、审计、审批、评测），通过收件箱路由交接。"Agent 要薄，平台要厚。"

## 10. Memory（记忆）⭐

| 类型 | 意思 | 实现 |
|---|---|---|
| 短期记忆 | 当前任务的上下文 | 对话历史、当前状态 |
| 长期记忆 | 跨会话保留的知识 | 数据库、向量库、摘要 |

**一句话答法**：
> "记忆不一定要向量库。结构化的业务数据直接存数据库最可靠；只有需要'语义回忆'时才用向量记忆。"

**和本项目的关系**：短期 = 每步从数据库重建；长期 = 数据库本身（工单历史、监控发现、经理纠错）。没用向量记忆，因为不需要语义回忆。改进点：长对话做摘要，而不是只保留最近 12 条。

## 11. Prompt / RAG / Fine-tuning 怎么选 ⭐⭐

| 方法 | 解决什么 | 成本 |
|---|---|---|
| 改 Prompt | 行为、格式、规则 | 最低，先试这个 |
| RAG | 模型**缺知识**（私有、最新） | 中 |
| Fine-tuning（微调） | 固定**风格/格式**、特定任务、降低延迟和成本 | 高，需要大量高质量数据 |

**一句话答法**：
> "先 prompt，缺知识加 RAG，prompt 和 RAG 都解决不了、且有大量数据时才考虑微调。知识用 RAG，行为用微调。"

## 12. LLM 安全（OWASP LLM Top 10）⭐⭐

重点几条：
| 风险 | 意思 | 本项目对策 |
|---|---|---|
| Prompt 注入 | 输入里藏指令劫持模型 | `<untrusted_message>` 包裹 + 注入标志 → 升级 |
| 敏感信息泄露 | 模型输出了不该给的数据 | RLS 多租户隔离；Sentry 脱敏；数据分级路由 |
| 过度授权（Excessive Agency） | Agent 权限太大 | 工具白名单 + 权限分级 + 审批工具不暴露 |
| 不安全的输出处理 | 直接执行模型输出 | Zod 校验；模型不执行代码 |
| 无限消耗 | 成本/资源失控 | 每日预算、限流、最大轮数 |

**一句话答法**：
> "最有效的防护不是让模型'更听话'，而是让它'就算被骗也做不了危险的事'——最小权限 + 代码决策 + 人工审批。"

## 13. 模型基础概念 ⭐

| 概念 | 一句话 |
|---|---|
| Token | 模型处理文本的最小单位，计费和上下文长度都按 token 算 |
| Temperature | 随机性；越低越稳定（分类、抽取用低值） |
| 上下文窗口 | 模型一次能看的最大 token 数 |
| 幻觉 | 模型自信地编造内容；成因是它在预测"像样的下一个词"，而不是查事实 |
| Stop reason | 模型为什么停：正常结束 / 达到长度上限 / 调用工具 / 拒答 |
| 延迟 | 首 token 时间 + 生成时间；流式输出改善体验 |

## 附：万能答题框架

被问到任何技术时：
1. **它解决什么问题**（一句话）
2. **怎么工作**（核心原理）
3. **代价/局限**
4. **我的项目为什么用/没用**
5. **什么条件下我会改变选择**

> 面试官要的不是"你用过多少框架"，而是"你知道每个技术解决什么问题，并能为自己的选择给出理由"。
