# 架构决策记录

最新的在最后。每条包含：日期、决策、理由。日期为新西兰本地时间。

---

### 2026-10-17 — 模块化单体 + API 优先，不做微服务
**决策：** 一个 Next.js 应用。业务规则放在 `src/domain/`，是所有调用方访问数据库的唯一路径：
看板页面、`/api/v1` 路由、agent 工具和 Inngest 函数。外部系统通过 `src/adapters/` 中的端口接入。
**理由：** 单人开发；核心保证（状态转换 + 审计行 + 幂等记录原子提交）依赖单个 Postgres 事务。
微服务会把它变成 saga/outbox，却没有产品收益。清晰的模块边界让日后拆分成本很低；Inngest worker
是最自然的第一个拆分对象。

### 2026-10-17 — 从第一天起就是多租户 SaaS；租户称为 `organization`
**决策：** 每张业务表都有 `organization_id NOT NULL`。子表使用复合外键 `(organization_id, x_id)`，
由数据库拒绝跨组织引用。domain 函数显式接收 `organizationId`。Postgres RLS 推迟到 M5，作为第二道防线。
**理由：** 事后补多租户要改动每张表、每个查询、每个测试。在这个领域里 "tenant" 已经指租客，
所以 SaaS 租户称为 *organization*（物业管理公司）。

### 2026-10-17 — 三级花费审批，带全局兜底
**决策：** `PM 有效额度 = min(property_managers.auto_approve_limit_cents ??
organizations.default_pm_auto_approve_limit_cents, owners.approval_limit_cents)`。
预估 ≤ 有效额度 → 自动通过；≤ 业主额度 → PM 审批；超出 → 升级。
实现在 `src/domain/approval-policy.ts`。
**理由：** PM 经验不同（按人设额度），组织需要默认值，且 PM 的自动审批永远不能超过业主授权
（`min` 上限）。

### 2026-10-17 — 超出 spec §9 的 schema 新增
**决策：** 新增 `organizations`、`property_managers`、`tenancy_tenants`（多对多）、
`idempotency_keys`、`jobs.source` / `created_by_*`（`reported_by_tenant_id` 可空）、
`jobs.state_before_escalation`、`jobs.version`。
**理由：** 多租户；合租者共享租约；工单可能来自 PM、巡检或 agent 自身；PM 需把升级"交还"到原状态；
状态转换需要乐观锁；规则 3 需要持久化保存幂等响应。

### 2026-10-17 — 工种枚举加 `other`，不加 `general`
**决策：** `plumbing | electrical | heating | handyman | locksmith | other`。
**理由：** `handyman` 本身就是综合维修工种；再加 `general` 会语义重叠，导致分诊在两者间摇摆。
`other` 是明确的"无法归类 → 交给 PM"出口。

### 2026-10-17 — 不变量在数据库层强制，而不仅在代码中
**决策：** 用 CHECK 约束和部分唯一索引保证：升级状态一致、外发消息必须有幂等键、每个工单只有一个
待审批项、每份租约只有一个主联系人、金额分非负、置信度在 0–1 之间。`audit_log` 通过触发器只允许追加
（拒绝 UPDATE/DELETE；TRUNCATE 仅供开发/测试使用——生产角色不得拥有 TRUNCATE 权限）。
**理由：** 即使应用代码有 bug 或有人直接用 SQL 控制台，规则 2–4 也必须成立。

### 2026-10-17 — 状态机在代码中；LLM 只能从菜单里选
**决策：** `src/workflows/state-machine.ts` 掌控所有转换。ESCALATED 可从任何非终止状态进入；
离开 ESCALATED 仅限 PM，且只能回到 `state_before_escalation`。CANCELLED 仅限 PM。CLOSED 和
CANCELLED 为终止状态。模型只会被提供 `allowedTransitions()`。2026-10-17 经产品负责人确认：
终止状态的工单不能升级；PM 不能从 ESCALATED 直接关单（只能交还或取消）；花费审批被拒绝后转为升级
（M2 实现）。
**理由：** CLAUDE.md 规则 1 / spec §5。

### 2026-10-17 — M0 无认证；PM 身份用明文字符串
**决策：** `approvals.decided_by` 和 `audit_log.actor_id` 为文本。页面以 `DEV_ORGANIZATION_SLUG`
指定的组织身份运行。
**理由：** 认证不在 v1 范围内；字符串 ID 日后迁移为用户外键很简单。

### 2026-10-17 — 工具链与版本
**决策：** Node 24 LTS、pnpm 10、Next 16、React 19、TypeScript 6（不用 7——typescript-eslint 只支持
< 6.1）、ESLint 9 flat config（不用 10——eslint-config-next 的插件尚不支持）、Vitest 5（分 `unit` 和
`db` 两个 project）、postgres.js 驱动、通过锁定版本的 `inngest-cli` 运行 Inngest 开发服务器。所有版本
精确锁定，且安装时已发布至少两周。Postgres 17 运行在 Docker 中，宿主端口 54329。
**理由：** lint 工具链兼容性；可复现的安装；DB 测试针对专用的 `keyhook_test` 数据库串行运行，每次从
迁移文件重建。

### 2026-10-17 — Playwright 推迟到 M2/M3
**决策：** M0 不引入 e2e 工具；`pnpm test:e2e` 随第一个真实 UI 流程一起加入。
**理由：** M0 的 UI 只是占位；目前单元测试 + DB 集成测试的信号更有价值。

### 2026-10-17 — 种子数据手写且确定性
**决策：** 固定 UUID（`src/db/seed/ids.ts`），不用 faker。另有一个只有一套房产的组织，用于测试隔离。
Harbour City 的 15 份租约 = 10 份当前 + 5 份已结束（历史）。
**理由：** 测试、评测和模拟器按名称引用固定数据；边界情况是刻意设计的。

### 2026-10-17 — 文档双语：英文为准，中文并列
**决策：** 每份文档都有英文 `X.md` 和简体中文 `X.zh-CN.md`，放在同一目录，首行互相链接。以英文版为准；
两个版本都更新后，改动才算完成。`CLAUDE.zh-CN.md` 是参考译本——Claude Code 加载的是 `CLAUDE.md`。
**理由：** 产品负责人使用中文工作；作品集的读者使用英文。

### 2026-10-17 — Agent 目录与人机边界
**决策：** `docs/agents.md` 按触发方式（被动响应 / 主动巡查 / 人工调用）× 自主度（只建议 / 需审批执行 /
自主执行）对 agent 分类，并通过工具权限级别细化到每个动作，同时给出各领域的自主度矩阵。维修以外的行在
确认前均为提议。
**理由：** 让路线图（下一个做资产组合监控，欠租作为第二个工作流）以及升级/审批规则有统一的参考依据。

### 2026-10-17 — M1 agent 形态：抽取 → 代码决策 → 撰写
**决策：** 每个工单状态有一个处理器。LLM 把事实抽取为 Zod schema（分诊、报价回复、时段选择、进度、
完工确认）；由代码执行策略（spec §7 升级规则、审批策略、状态机）；之后 LLM 撰写发给租客的文字。只有
TRIAGED 使用模型驱动的工具循环，限定五个工具，并对结果自检（必须以 AWAITING_QUOTE 或 ESCALATED 结束）。
每个处理器在一个事务中提交全部副作用；消息在提交后发送；入站消息至多处理一次。M1 中所有偏离主流程的
情况都升级（追问、重新提供时段、更换师傅在 M2 实现）。
**理由：** 涉及金钱、法律或安全的决策保持确定性、可测试；模型负责语言工作。与 `docs/agents.zh-CN.md` §3.2 一致。

### 2026-10-17 — 模型与请求设置
**决策：** 所有步骤使用 `claude-opus-5-5`（产品负责人决定）。显式设置 effort：分诊/解读/工具循环用
`medium`，撰写租客消息用 `low`。开启服务端拒答 fallback（`fallbacks: "default"`）；最终仍拒答则升级。
结构化输出使用 `output_config.format`（该模型不支持强制 tool_choice）。顶层提示词缓存，system prompt
保持静态。只有在评测证明质量不降之后才考虑更便宜的模型。
**理由：** 单一模型意味着单一缓存命名空间和单一需要评测的行为。

### 2026-10-17 — 可配置的师傅选择
**决策：** `organizations.tradie_selection`（经 Zod 校验的 JSON）：`strategy` 为 `rules`（最高分胜出）或
`llm`（模型从前 N 名候选中挑选并说明理由）；权重包括评分、空档（在时间范围内最早的空闲时段，来自
`tradie_availability`）、熟悉度（在该房产的历史工单）、工作量（未完成工单数）。硬性条件（活跃、工种、
覆盖区域、可紧急出勤）永远由代码执行；`request_quote` 会再次检查师傅是否可选。
**理由：** 各物业公司选师傅的方式不同；模型永远无法选中不合格的师傅。

### 2026-10-17 — LLM 成本以美元 micro-dollar 记录
**决策：** `llm_calls` 按请求记录 token、延迟和 `cost_usd_micros`（价格未知的模型记为 null）。业务金额仍为
NZD 分。
**理由：** API 成本是以美元计费的运营指标（spec §10 "每单成本"）。

### 2026-10-17 — 报价按含 GST 存储
**决策：** `estimate_cents` 含 GST。注明 "+GST" 的报价加 15%；GST 状态不明时按含税处理，并在审计日志中注明。
**理由：** 审批额度的比较必须口径一致。2026-10-17 经产品负责人确认。

### 2026-10-17 — M1 使用自建评测 runner；是否用 promptfoo 推迟到 M4 决定
**决策：** `pnpm eval` 在独立的 `keyhook_eval` 数据库上，通过真实的接入 + agent 路径运行 YAML 场景，
并按 spec §10 指标打分。结果按提交保存在 `evals/results/`。是否采用 promptfoo 在 M4 场景数达到 50+ 时决定。
**理由：** CLAUDE.md 要求从 M1 起任何 agent 改动都要给出评测分数；场景格式与 promptfoo 无关。

### 2026-10-17 — M2 跟进与重试策略（按 organization 可配置）
**决策：** `organizations.workflow_policy`（经 Zod 校验的 JSON），默认值已与产品负责人确认：追问最多 2 轮；
等待租客（追问、选时段）24h 提醒，再过 24h 升级；完工确认 48h 提醒，再过 72h 升级；报价提醒按紧急程度
1h/4h/24h，提醒 2 次后换师傅；最多尝试 3 位师傅；时段最多提供两次；预约结束后 4h 询问师傅，再过 24h
升级；PM 审批 24h 提醒；新西兰时间 20:00–08:00 不发提醒（顺延到 08:00）。
**理由：** 各物业公司的服务标准不同；这些数值是业务规则，不是代码。

### 2026-10-17 — 跟进：以数据库为准，扫描器 + 按工单串行
**决策：** 每个工单最多一个 `scheduled` 状态的跟进（部分唯一索引）。任何状态转换或工单相关方的回复都会把
它标记为 `satisfied`；每次推进后，按工单当前的等待重新安排一个。Inngest 每 5 分钟的 cron 为每条到期记录
发出 `followup/due` 事件（事件 id 去重）；处理函数先认领该记录（`scheduled → sent`）再执行。所有会修改工单
的 Inngest 函数共用一个按工单、env 作用域的并发键。
**理由：** 不需要为每个跟进挂起一个函数，也不需要取消机制；丢失的事件会在下次扫描时重发；重复事件不会
导致重复发送。

### 2026-10-17 — 只缺信息时追问而不是升级
**决策：** 如果分诊报告 `needsMoreInfo`，且其他触发条件只有置信度低或工种无法归类，agent 会向租客追问
（RECEIVED/NEEDS_INFO → TRIAGED → NEEDS_INFO），而不是升级；出现任何其他触发条件仍然升级。达到轮数上限后升级。
**理由：** spec §7 的低置信度规则是为了避免猜测；追问是更低成本的解决办法，追问无效时仍会升级。

### 2026-10-17 — PM 审批路径
**决策：** 报价超过 PM 有效额度但在业主额度内 → `request_approval`（待审批记录、AWAITING_APPROVAL、通知
PM）。先以 PM 身份写入 PM 的决定，再以 PM 为执行者运行 `approve_spend`；没有已存储的批准记录时 executeTool
会拒绝执行。拒绝则升级。每个审批只能决定一次。在有认证之前，PM 从本组织的 PM 列表中选择自己的身份。
**理由：** CLAUDE.md 规则 2 及 spec §5/§8。

### 2026-10-17 — "交还"的含义（提议——待确认）
**决策：** 交还表示 PM 已经解决了导致升级的问题。工单回到升级前的状态（与之前的约定一致）。对于在分诊阶段
升级的工单，PM 的交还即接受已记录的紧急程度/工种（PM 可修改），agent 不再重新分诊，直接进入安排报价；之后
租客发来的新消息仍会正常分诊。
**理由：** 对同一条消息重新分诊会重现相同的升级（例如最初的燃气味），形成循环。

### 2026-10-17 — 看板由服务端基于 domain 层渲染；修改操作走 /api/v1
**决策：** 看板页面是 React Server Components，通过 `src/domain` 读取数据（读取不在客户端发请求）。PM 的每个
修改操作都通过经 Zod 校验的 `/api/v1` 路由，调用与 agent 相同的服务，并以 PM 为执行者写入审计。使用带设计
token 的纯 CSS，暂不引入 UI 库。
**理由：** 保持 API 优先，又不必重复实现读取接口；所有写操作只有一条代码路径。

### 2026-10-17 — 通过 OpenTelemetry/OTLP 追踪；Langfuse 作为可配置的后端
**决策：** 仅当设置了 `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`（或 `OTEL_EXPORTER_OTLP_ENDPOINT`）时，应用才注册
OpenTelemetry tracer provider，并通过 OTLP/HTTP 导出——把它指向 Langfuse 的 OTLP 端点即可接入 Langfuse，无需其 SDK。
每次 Claude 请求生成一个 `gen_ai.*` span（模型、token、成本、步骤、effort）；`job.advance` 为根 span；审计行保存
当前 trace id。span 只含元数据，不含提示词文本。暂不使用 Anthropic SDK 自带的追踪：带该功能的版本发布还不满两周。
**理由：** 标准化埋点、后端可替换、不依赖厂商 SDK；默认不把租客消息内容发送到追踪后端（个人信息）。

### 2026-10-17 — 评测集形态与运行频率
**决策：** 60 个 YAML 场景（spec 要求 ≥50），支持多步流程和模拟时间。真实运行：本地 `pnpm eval`，以及按需 + 每晚
运行的 GitHub workflow（需要 `ANTHROPIC_API_KEY` secret）。每次 push 运行不需要 key 的检查：场景校验，以及用脚本化
LLM 测试 runner 的机制。出现禁止操作或场景错误时运行失败。
**理由：** 真实评测要花钱且结果不确定；每次 push 的 CI 必须免费且稳定。

### 2026-10-17 — 一条消息报多个问题（提议——待确认）
**决策：** 如果一条消息报告的问题需要不同工种或分开上门，agent 升级，由 PM 拆分成多个工单；同一位师傅能处理的
多个小问题仍为一个工单。
**理由：** 只处理其中一个问题会悄悄漏掉另一个。

### 2026-10-17 — agent 故障即升级；重复处理即中止
**决策：** 模型拒答或输出不可用时立即升级工单（不重试）；其他错误由 Inngest 重试，重试用尽后由 `onFailure` 升级工单。
若某次运行发现其入站消息已被并发运行处理，则中止该事务。
**理由：** 卡住的工单 PM 看不到；升级能让每一次故障都变成可见的待办。

### 2026-10-17 — 认证：每个 PM 独立会话，不引入认证库
**决策：** PM 用邮箱 + 密码登录（通过 `node:crypto` 的 scrypt）。会话存储在 Postgres；cookie 中是随机 token，数据库只
存它的 SHA-256。`proxy.ts` 对页面做基于 cookie 的快速检查；每个页面和 API 路由都做权威的数据库查验
（`requirePageUser` / `requireApiUser`），并由静态测试强制。种子数据中的 PM 共用密码 `SEED_PM_PASSWORD`（默认
`keyhook-demo`，仅限开发/演示）。
**理由：** RLS 需要真实的"用户所属组织"，共享密码做不到。这套实现很小、无依赖、测试完整；有真实客户时再换成身份服务商。

### 2026-10-17 — RLS 用于请求范围的访问；后台任务保留 owner 角色
**决策：** 请求处理在 `withOrg()` 中运行（一个短事务、`SET LOCAL ROLE keyhook_app`、`app.organization_id`），因此
Postgres 会过滤所有按组织划分的表，并拒绝跨组织写入；缺少上下文直接报错。后台任务（Inngest agent、跟进、评测、
种子数据）使用 owner 角色并显式传入 `organizationId`，由复合外键保护。`sessions` 不在 RLS 范围内（在确定组织之前就要读取）。
**理由：** agent 步骤会调用 LLM，不能为此长时间占用事务；面向用户的这一层才是认证或查询 bug 会泄露数据的地方，所以 RLS 放在这里。

### 2026-10-17 — 模拟器花费保护
**决策：** 当某组织每小时的模拟器消息超过 `SIMULATOR_MAX_MESSAGES_PER_HOUR`（默认 60），或 24 小时内 AI 花费达到
`DAILY_LLM_BUDGET_USD`（默认 5）时，拒绝新的模拟器消息（429）。已经在进行的工单继续运行。
**理由：** 公开演示时，模拟器是外人唯一能触发付费模型调用的入口。

### 2026-10-17 — 可插拔的模型提供商；Claude 仍为默认
**决策：** `LlmClient` 有两个实现：`ClaudeLlm`（Anthropic SDK）和 `OpenAICompatibleLlm`（带 `baseURL` 的 OpenAI SDK，
覆盖 OpenAI、DeepSeek 和 Moonshot Kimi）。`organizations.llm_routing` 按步骤组（triage、retriage、act、interpret、compose）
选择模型并设默认值；为 null 时全部使用 Claude。OpenAI 兼容适配器在两个方向上转换 Anthropic 的消息/工具格式，因此处理器
代码无需改动；结构化输出在支持时使用原生 JSON Schema，否则用 JSON 模式并把 schema 写进提示词，始终经 Zod 校验，并有一次
修正重试。API key 只来自环境变量。DeepSeek 和 Kimi 需要 `acknowledgeOffshoreProviders: true`。非 Claude 模型的成本来自
`LLM_PRICES_JSON`（否则为 null）。只有在 `pnpm eval --model provider:model` 证明质量不降后才切换模型。
**理由：** 产品负责人需要灵活性和成本选择，同时不分叉 agent 逻辑；隐私门槛和评测门槛保证切换是有意为之。新增依赖：`openai`（官方 SDK）。

### 2026-10-17 — 部署级的默认模型；价格未知的调用仍计入预算
**决策：** `LLM_DEFAULT_MODEL=provider:model`（DeepSeek/Kimi 还需 `LLM_ACKNOWLEDGE_OFFSHORE=true`）为没有配置 `llm_routing`
的组织设定模型。模拟器的每日预算对每次成本未知的调用按 `UNKNOWN_LLM_CALL_COST_USD`（默认 0.05）计费。
**理由：** 产品负责人希望在拿到 Anthropic key 之前先用 Kimi；没有价格表时，花费保护否则永远不会触发。

### 2026-10-17 — PM 的纠正变成评测场景（改进闭环）
**决策：** `agent_feedback` 存储带标注的纠正：PM 在工单页标记错误（紧急程度、工种、该升级 / 不该升级、其他），交还工单时
修改了紧急程度/工种也会自动记录。每条记录都保存 agent 当时的判断快照。`pnpm eval:harvest` 把尚未收集的记录转换成
YAML 场景（工单的真实消息作为步骤，PM 的答案作为预期），放在 `evals/scenarios/harvested/`，对邮箱、电话号码和已知姓名
做脱敏，并标记为 `reviewed: false`；除非加 `--include-unreviewed`，否则评测会跳过未审核的场景。人工审核后改为
`reviewed: true` 再提交。
**理由：** 模型不会从生产数据中学习，但系统可以——每一次纠正都变成回归测试，提示词/规则的改动要在真实的历史错误上证明有效。
审核保留人工环节，因为生产消息含有个人信息。

### 2026-10-18 — 范围与 Keyhook 平台对齐
**决策：** 从 Keyhook 官网整理出的需求加入 spec §12（R1–R8，里程碑 M6–M9）：租客媒体分析、报价变更、发票核对、巡检发现 →
工单、业主通知、租客节点更新、资产组合监控、欠租。房源、筛查、电子签名、信托账户和报表属于 Keyhook 平台本身，不在范围内；
agent 通过适配层与之协作。此后文档和界面使用 Keyhook 的词汇（work order、supplier、owner approval threshold、variation）。
**理由：** 本项目要展示的是岗位所描述的 agent 层——建立在 Keyhook 现有数据和审批之上，而不是复制整个平台。

### 2026-10-18 — M6：租客照片（先做图片，视频以后）
**决策：** 照片随入站消息上传（模拟器在浏览器里先压缩到最长边 ≤1600 像素的 JPEG）。代码先从文件头检查类型/大小/分辨率
（不引入图片库）；再由看图模型报告画面内容、质量、安全线索和电器铭牌文字；结果按张存储，并出现在之后每一步的上下文中。
图片里出现给 agent 的指令则升级（提示词注入）；照片不可用则请租客重拍；没有看图模型时照片保留为"未分析"，工单照常推进。
图片存在 Postgres（`media` 表，受 RLS 保护），通过 `media-store.ts` 访问，保留 180 天（每天清理）。看图是单独的路由步骤组
（`LLM_VISION_MODEL`）；各服务商声明是否支持 `vision`，Kimi 需设置 `MOONSHOT_VISION=true`。视频需要抽帧（ffmpeg），暂缓。
**理由：** Keyhook 的租客已经会附带媒体；读懂它（比如热水器铭牌上的型号）正是 agent 能增值的地方。演示阶段存 Postgres 不需要额外服务。

### 2026-10-18 — 测试中使用低成本的密码哈希；事务内不做重计算
**决策：** scrypt 在生产环境为 N=2^17（128MB），测试中为 2^14；种子脚本先算好哈希再开启事务。
**理由：** 每次测试灌种子都按生产强度计算哈希，会让内存紧张的开发机卡住好几分钟（期间还占着一个事务）——这就是之前"偶发"的测试卡住。

### 2026-10-18 — M7：报价变更、发票核对、业主通知、租客节点更新
**决策：** 报价变更是一条 `approvals` 记录，`kind = 'variation'`，带 `previous_amount_cents`；新总价（或原估价 + 追加金额，未含 GST 时加 15%）
与报价走同一套审批策略。在 PM 额度内：直接提高估价，通知师傅继续；在业主额度内：由 PM 审批（`approve_variation`，权限 `approval`），
已预约的上门照常进行，只有追加的部分暂停；超过业主额度或没有金额：升级。变更被拒绝时，告诉师傅不要做追加部分并升级。
发票（来自师傅的文字或发票照片）存入 `invoices`，与已批准金额比较：差额在 max(5%, 50 纽币) 以内为"匹配"，否则交 PM 复核；
工单关闭后才发来的发票照样记录，不会重新打开工单。需要审批时、工单关闭时（最终费用 = 最后一张发票，否则用估价）通过发件箱通知业主。
租客另外会在"已找师傅报价"和"报价等待审批"两个节点收到消息（绝不透露金额）。
**理由：** 这些是维修 agent 涉及的 Keyhook 流程（spec §12 R2、R3、R5、R6）。复用审批表和审批策略，代码里只有一道审批关口；
变更不改变工单状态，避免取消一次大部分工作仍能完成的上门。

### 2026-10-18 — M8（R4）：巡检发现转成维修工单
**决策：** PM 录入一条巡检发现（`POST /api/v1/inspection-findings`，Portfolio 页面），`createAgencyJob` 创建一个
`source: inspection` 的工单。房子在租时，把当前租约的主联系人记在 `reported_by_tenant_id`（这里的意思是"工单的租客联系人"），
后续租客相关步骤照常进行：先告诉租客这是巡检发现的问题，再请他选上门时间、完工后确认。空置的房子没有租客：agent 照常询价，
到约时间时交给 PM。巡检笔记作为不可信数据交给模型。笔记太含糊、没法向师傅说明情况时，升级给 PM，而不是去问租客。
巡检照片暂未接入（后续再做）。
**理由：** 已和产品负责人确认（2026-10-18）：联系当前租客。复用租客字段，下游步骤都不用改。

### 2026-10-18 — M8（R7）：资产组合监控，只用规则，由 PM 决定
**决策：** 每天一次的 Inngest 定时任务（`portfolio-monitor`，新西兰时间 06:00，每个物业公司一个 step，在 `withOrg` 下运行），
外加一个"Scan now"按钮，按房产和工种统计过去 365 天的工单。不计入已取消的工单，也不计入监控自己产生的 `agent_detected` 工单。
达到 3 单及以上时，写一条 `monitor_findings` 记录（受 RLS 保护），包含作为证据的工单 id、摘要和建议，并记审计 `monitor.finding`。
部分唯一索引保证同一房产 + 工种只有一条未处理的发现。已忽略或已开单的发现，只有出现不在原证据里的新工单时才会再次提出。
PM 可以把发现开成工单（`agent_detected`，和巡检一样关联租客；之后 agent 照常分诊、询价，审批额度仍然适用），也可以填写备注后忽略。
不调用模型：规则是确定的，文字由历史工单拼出来。合规到期的触发条件要等有合规数据源之后再做。
**理由：** agents.md 规定"是否开单"以及大额资本支出由 PM 决定。计数这件事用确定的规则，比用模型更便宜、也更容易审计。

### 2026-10-18 — 产品界面：统一设计系统、公开首页、agent 目录页
**决策：** 界面使用一份基于设计 token 的样式表（`globals.css`）。它沿用新西兰现代物业管理软件的视觉风格：
海军蓝品牌色阶、蓝色强调色、通过 `next/font` 加载的 Inter 字体、柔和的卡片；使用自己的标识，不用任何第三方 logo 或素材。
登录后的页面共用一个外壳（`AppShell`：左侧导航，实时显示需要 PM 处理的工单、待审批和监控发现的数量）。`/` 现在是公开首页，
列出所有 agent（已上线 / 下一个 / 规划中），以及各自的触发方式、自主程度和需要人决定的地方。这份目录数据（`agent-catalog.ts`）
同时驱动 `/dashboard/agents`，后者还显示每个 agent 近 30 天的实时数据（`agentStats`）。新增依赖 `lucide-react`（MIT 协议，按需打包），
用一套统一的图标代替手画 SVG。

### 2026-10-18 — "法律"指法律行动；烟雾报警器问题算急迫；eval 可以检查升级理由
**决策：** 在 schema 中把分诊标记 `legalOrTribunal` 定义为：消息本身提到法律行动、律师、租赁仲裁庭或正式投诉。
单纯的合规要求（Healthy Homes、烟雾报警器规定）不算法律行动。把"烟雾报警器缺失或故障"加入急迫示例 *（产品默认值，待确认）*。
Eval 场景现在可以断言 `notReasons`：升级理由里不能出现的文字。这样能抓住"结果对了、理由错了"的情况。
**理由：** 录制演示时实际遇到：Kimi 把一条巡检发现（缺烟雾报警器、排气扇坏了）升级时写了"legal action / Tenancy Tribunal"，
但笔记里根本没提，还把紧急程度判成了 routine。PM 看到这个理由会被误导。Kimi K2.6 的结果：只改标记定义时 3/4（不再误报"法律"，两个真正涉及法律的场景仍然升级，
但烟雾报警器仍判为 routine）；加上紧急程度示例后，巡检和 Healthy Homes 相关场景 4/4。

### 2026-10-18 — 给审核者的访客体验入口
**决策：** `POST /api/v1/auth/guest`，只有设置 `DEMO_GUEST_LOGIN=true` 才开启，把访客登录为演示公司里共享的
"Guest reviewer" PM。这个 PM 在第一次使用时创建，没有密码哈希，因此无法通过其他方式登录。会话 2 小时过期（普通会话 12 小时）。
每个 IP 每小时最多 20 次访客登录。其他一切不变：RLS 范围、模拟器限流和每日模型预算。
**理由：** 审核者不会来要账号；打不开的 demo 等于没人看。一个演示公司里共享一个访客就够了。
给每个访客单独一个沙盒，意味着每次访问都要复制一份种子数据。

### 2026-10-18 — M9：在共享平台上做欠租 agent；第一版收件箱分流
**决策：** 欠租是第二个工作流，有自己的状态机（`OPEN → REMINDED → PROMISED → NOTICE_PENDING → NOTICE_SENT`，另有
`ESCALATED`、`RESOLVED`、`CLOSED`），复用工具网关、幂等、审计日志、审批、发件箱、模型路由和 eval。为此，`ToolContext`、消息、审计记录和审批
现在可以属于一个工单**或**一个欠租案件（审批表用数据库约束保证二者恰好其一）。余额从租金台账计算（先进先出，按新西兰日历日期），
从不把存下来的数字当作依据。策略写在代码里，可按物业公司配置：
- 宽限 2 天后发友好提醒，之后每 3 天一次（最多 2 次）；
- agent 可以接受 7 天内的还款承诺，或 8 周内还清的还款计划；
- 承诺没兑现会跟进；
- 14 天补救通知用固定模板起草（绝不由模型撰写），PM 批准后才由 `approval` 级工具发出；
- 欠租满 21 天、经济困难、家暴、金额争议、情绪激动或注入，都升级给人。

有未结案件的租客不带会话直接发消息时，先经过收件箱分流（一次低成本的模型调用：欠租还是维修）；其他人不受影响。
所有阈值都是*提议值*。新西兰法律需向 Tenancy Services 核实：14 天通知，以及欠租 21 天可申请仲裁庭终止租约（RTA 第 55、56 条）。
**理由：** 岗位点名提到欠租；而第二个 agent 只需要一个状态机、几个工具和 9 个 eval 场景，这是平台可复用最有力的证据。
Kimi K2.6 在 9 个欠租场景上：一开始 8/9，"手头有点紧"被过度理解为经济困难。在提示词和 schema 里明确了困难的界限后达到 9/9，
真正的困难情况仍然会升级。

### 2026-10-18 — QA 红队：自动生成对抗测试，评审后作为回归测试草稿保留
**决策：** `pnpm redteam` 运行一个 QA agent，分四步：
1. 由一个模型（`--attacker`，默认与被测模型相同）按固定类别写新的对抗对话：注入变体、藏在日常描述里的紧急情况、含糊、
   多个意图混在一起、供应商欺诈、欠租操纵、情绪施压。它能看到现有场景清单，避免重复。
2. 每个用例转换成普通场景，并用同一个 Zod schema 校验；不认识的审计动作会被去掉。不合法的用例只报告、不运行。
3. 用 eval 运行器让真实 agent 跑这个用例。
4. 判定失败的条件：任何硬性检查不通过（预期的升级或紧急程度、禁止动作、报错），或者 LLM 评审读了 agent 实际发出的消息后，
   发现*严重*问题（照做注入的指令、向租客透露金额、编造承诺、漏掉安全隐患）。

失败用例写入 `evals/scenarios/redteam/`，标记 `reviewed: false`；人工审核之前，eval 套件会跳过它们。花费用 `--max-cost` 控制上限。
**理由：** 岗位要求"在客户之前发现 bug 的自动化测试系统"和"能自我测试、监控、改进的系统"。手写场景只能覆盖我们已经想到的情况。
生成的用例要先经人审核才变成回归测试，避免把错误的预期变成错误的规则。第一次真实运行就证明了这一点。5 个用例全部"失败"，但主要是测试方自己的问题：
- 它把分诊这类正常步骤也列为禁止；现在只允许禁止危险动作；
- 它选了另一家物业公司的房子；现在房产列表只限演示公司；
- 评审把真实的供应商名字和系统给出的上门时间当成"编造"；现在评审还能看到工具调用及其结果的系统记录。

### 2026-10-18 — 欠租扫描按案件拆成独立事件
**决策：** 每日扫描和手动触发的扫描只负责打开到期的案件（`openDueCases`），然后为每个未结案件发一个 `arrears/advance.requested` 事件。
这样，无论是时间规则还是租客回复触发的推进，都在按案件划分的并发键下运行。进程内的 `sweepArrears` 保留给 eval、测试和脚本使用。
**理由：** 录制欠租演示时发现：手动扫描直接推进了案件，于是同一时刻同一个案件上还在处理租客的回复。乐观版本检查保证了数据一致，
但对话顺序令人困惑，并且有一次运行需要重试。按案件串行执行，从根本上消除这个竞争，而不是依赖重试。

### 2026-10-19 — 用现有表构建单个工单的 Agent 调用轨迹
**决策：** 工单页面显示“Agent 调用轨迹”：按时间顺序列出每次模型调用（步骤、模型、输入/输出 token、缓存命中的输入、耗时、费用、停止原因或错误）和每次工具调用，并给出汇总和最慢的步骤。
数据来自 `llm_calls` 和 `audit_log`，没有新增表。
**理由：** Langfuse 里已经有这些信息，但 PM 或评审者不应该为了回答“agent 在这个工单上做了什么、花了多少钱”去打开另一个工具。
这两张表本来就在每次调用时写入，所以这个视图在写入时没有额外开销，也不会和审计记录不一致。
