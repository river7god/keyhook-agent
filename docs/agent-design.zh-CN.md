# 构建生产级 agent：常见问题与本项目的解决方式（2026-10-18）

讲把 LLM agent 放进生产环境时最难的那些部分，以及本项目在每一处的选择。写给审核者和后续的贡献者。系统整体形态见
[`architecture.zh-CN.md`](architecture.zh-CN.md)；每个具体决策见 [`decisions.zh-CN.md`](decisions.zh-CN.md)。

**一句话概括：** 这是一个*事务型* agent 系统（涉及钱、法律通知、别人的家），所以设计上把可靠性和安全放在代码里——状态机、持久化工作流
和工具网关——而把模型限制在"理解"和"撰写"上。

---

## 1. 工作流还是 agent？模型在哪里可以做决定

任何 agent 最重要的设计选择是：**下一步由谁决定**。

| 模式 | 模型决定什么 | 适合 | 风险 |
|---|---|---|---|
| 带 LLM 步骤的工作流 | 步骤内部的事（分类、提取、撰写） | 已知的业务流程 | 低：每条路径都在代码里 |
| 有限的工具循环 | 从一小份清单里选工具，选几次 | 在系统给出的选项中挑选 | 中：需要上限和自检 |
| 自主 agent / 规划者 | 计划和下一步 | 开放式研究、写代码 | 高：难测试、难审计、难约束 |

**这里的规则：模型负责提取和撰写，代码负责决定。** 每个处理器都遵循*提取 → 代码决策 → 撰写*（决策日志 2026-10-17）：

```
租客消息 ──► LLM：结构化提取（紧急程度、工种、各种标记）─┐
                                                         ├─► 代码：策略（decideTriage、decideApproval、
系统事实 ────────────────────────────────────────────────┘          decideReply）─► 通过 executeTool 调用工具
                                         LLM：撰写消息 ◄────┘
```

满足以下任意一条就放进**代码**（[`agents.zh-CN.md`](agents.zh-CN.md) 第 5 节的四条标准）：

- **不可撤回**：法律通知、付款；
- **影响大**：钱、安全、租约；
- **可以校验**：花费额度、日期规则；
- **有人要为它负责**：PM 或业主。

以下情况交给**模型**：输入是非结构化的（消息、照片、发票），输出是给人看的，或者是在系统给出的选项中挑选、并且结果会被校验。

| 本项目中 | 由谁决定 |
|---|---|
| 工单/案件的下一个状态 | 代码：`src/workflows/state-machine.ts`、`arrears-state-machine.ts` |
| 花费：自动批准 / PM 审批 / 升级 | 代码：`src/domain/approval-policy.ts`（整数分） |
| 升级规则 | 代码：`src/agent/policy.ts` |
| 欠租：这个承诺或计划能不能接受？ | 代码：`src/agent/arrears/advance.ts` 里的 `decideReply` |
| 14 天通知的措辞 | 代码：固定模板（`noticeText`），绝不由模型撰写 |
| 租客说了什么、照片里有什么 | 模型：结构化输出，经 Zod 校验 |
| 联系哪个符合条件的师傅 | 模型，在**唯一**的工具循环里（TRIAGED）：最多 8 轮，之后自检状态是否真的推进了 |
| 消息的措辞 | 模型，只能依据给定的事实 |

## 2. 状态、持久化与长时间任务

**问题：** 真实的工作要等几小时甚至几天（师傅的报价、租客的回复）。把状态放在内存或聊天记录里，重启、重试、部署之后就丢了。

**常见做法：** 框架的检查点（LangGraph 的 checkpointer）、持久化执行引擎（Temporal、Inngest、AWS Step Functions），
或者把状态存在自己的数据库里再配一个调度器。

**这里：**

- **状态存在业务表里**（`jobs`、`arrears_cases`）：后台、审计日志和 agent 读的是同一份数据。只有一个依据，而不是数据旁边再放一份检查点。
- **Inngest** 运行工作流（`src/workflows/functions/`）：
  - 由事件触发每一步；
  - 每个工单、每个案件并发为 1，两次运行不会同时推进同一件事；
  - 自动重试；`onFailure` 会升级给 PM，而不是悄悄失败；
  - 定时扫描负责跟进（每 5 分钟）、欠租（每天）、Portfolio Monitor 和数据保留。
- **跟进是数据库里的记录**（`follow_ups`）：定时扫描，*先认领再执行*，等待的回复到达后自动取消。
- **任务拆解在设计时完成。** 一个工单的生命周期拆成约 12 个状态，一个欠租案件拆成 8 个。每一步只调用一两次模型，目的很窄。
  只有开放式任务（红队生成用例）才在运行时规划。

## 3. 工具调用与 Function Calling

**问题：**

- 模型调错工具或编造参数；
- 重试导致副作用重复（发两条短信、约两次）；
- 工具能做的事超出模型应有的权限；
- 没有记录动作为什么发生。

**这里，所有工具调用都经过同一个网关：** `executeTool`（`src/tools/execute.ts`），无论调用方是模型还是工作流代码。它负责：

1. **类型化输入**：每个工具一个 Zod schema，转成 JSON Schema 交给模型。输入不合法会返回结构化错误，模型可以据此修正。
2. **权限级别** `read | auto | approval`（CLAUDE.md 第 2 条）。`approval` 级工具只有在该工单或案件存在 PM 审批记录时才执行，而且**从不暴露给模型**
   （`toAnthropicTool` 会直接抛错）。
3. **幂等**：键由工单版本加上触发它的消息、跟进或审批组成。工具和幂等键在同一个 savepoint 里执行，调用失败时两者一起回滚。
4. **每次调用一条审计记录**：谁、做了什么、为什么、输入、输出、结果、trace id，写入只追加的表（数据库触发器拒绝修改）。

在唯一的工具循环之外，模型只返回**结构化输出**（`output_config.format`，经 Zod 校验），由代码调用工具。这比让模型自由调用工具更可预期。
同一套工具定义可以用于 Claude、OpenAI、DeepSeek 和 Kimi（`src/agent/providers/`）。

## 4. 人在环中（Human-in-the-loop）

**问题：** "请人来决定"必须能跨越好几天、有多个人参与、经得起审计，而且 agent 不能绕过它。

**这里：**

- **审批记录**：审批存在 `approvals` 表里（报价、报价变更、欠租通知）。PM 在后台决定 → `recordApprovalDecision` →
  以 PM 身份执行 approval 级工具 → 记入审计。
- **升级是一个产品界面**，而不是一句"请联系某人"。每次升级都附带摘要、已做的事、建议和证据，PM 约 30 秒就能做决定。
- **交还**：PM 可以把工单交还给 agent，但只能回到它离开时的状态。
- **每个动作的人机边界都写清楚了**（[`agents.zh-CN.md`](agents.zh-CN.md) 第 5.2 节）。路线图里会把自主程度做成每家公司可调的设置：
  建议 → 审批 → 执行。
- **AI 写的测试也要人检查**：红队发现的问题和 PM 的纠正都先存为 `reviewed: false` 的场景，由人确认后才生效。

框架的做法是 LangGraph 的 `interrupt()`：暂停图的运行，等恢复。这里选择审批*记录*，是因为审批要跨好几天、需要多个 PM 参与，还必须可审计。

## 5. 不可信输入与提示词注入

**问题：** 租客和供应商可以写任何内容，包括给 agent 的指令，可能在文字里，也可能在图片里。

**这里**（CLAUDE.md 第 5 条）：

- 所有入站文字都包裹成 `<untrusted_message>`，内容里的闭合标签会被去掉，系统提示词说明这是数据（`src/agent/untrusted.ts`）。
- 提取 schema 里有 `promptInjection` 标记。一旦标记，工单就升级，并且**什么都不发**。照片里的文字（看图那一步）和欠租回复也一样。
- 即使模型被骗，也拿不到危险的能力：approval 级工具不暴露给模型；策略由代码计算；工具输入都经过校验。
- 有 eval 场景覆盖（隐藏的额度、角色扮演、报价或报价变更里的注入），红队也会持续生成新的注入变体。

## 6. 隔离与沙箱

**什么时候需要沙箱：** 会执行生成代码或访问任意网站的 agent（写代码的 agent、数据分析 agent、深度研究 agent），
必须在隔离、用完即弃的环境里运行这些代码：

- Docker、gVisor 或 Firecracker 微虚拟机，或托管的沙箱服务；
- 默认断网；
- 只读、短期有效的凭证；
- 限制 CPU、内存和运行时间；
- 输出当作不可信数据。

**这里，没有任何 agent 执行代码。** agent 只能调用一份固定的、有类型的工具白名单。所以隔离在其他层面实现：

| 层 | 控制 |
|---|---|
| 能力 | 带 schema 和权限级别的工具白名单；没有 shell，没有任意 HTTP |
| 数据 | 每行都有 `organization_id`、复合外键、通过专用角色的 Postgres 行级安全（默认拒绝） |
| 输入 | 不可信内容单独包裹；注入标记会升级 |
| 外发 | 消息经过适配器（开发环境用模拟发件箱，第 7 条） |
| 隐私 | 海外模型服务商需要明确同意（新西兰 Privacy Act IPP 12）；错误上报到 Sentry 前先脱敏 |

**什么时候会变：** 路线图里的工程 agent（跑测试、提出修复）会执行代码。这类 agent 必须在一次性容器里运行，不能有生产凭证，
它们的改动要经过 PR 评审。

## 7. 输出可靠性

| 问题 | 这里的控制 |
|---|---|
| 输出格式错误或不完整 | 结构化输出 + Zod 校验。不匹配会抛出 `LlmOutputError`，工单升级 |
| 模型拒答 | 检测到（`stop_reason: refusal`）就升级，绝不盲目重试 |
| 服务商故障、key 无效、余额不足 | 永久性错误（认证、欠费）立即升级；临时错误按退避重试 |
| 消息里出现编造的事实 | 撰写时给出明确的事实清单。规则：除非事实里写了，否则不能说"已安排"（红队发现后加上的） |
| 结果对了、理由错了 | eval 的 `notReasons` 检查升级理由，不只检查结果 |
| SDK 的意外行为 | 测试在假的 HTTP 层上运行真实 SDK（借此发现了一个被类型声明掩盖的 `withResponse` 问题） |

## 8. 评测：证明它能用，并且一直能用

**问题：** 提示词和模型会变，质量会悄悄下降，演示只展示顺利的路径。

三层，每一层都能抓到其他层漏掉的问题：

1. **代码测试**（290 多个，Vitest，很多连真实的 Postgres）：状态机、策略、RLS 隔离、并发、幂等、注入处理，并用脚本化模型测试确定性流程。
2. **场景 eval**（83 个 YAML 场景，`pnpm eval`）：用真实模型跑多轮对话，评分项包括紧急程度、工种、升级精确率和召回率、最终状态、
   必须执行的动作、回复语言和升级理由。**禁止动作必须为 0。** 结果按提交和模型保存。花费上限和 17 个场景的抽样集
   （`eval:smoke`，约 1 美元）让它足够便宜。
3. **发现未知的失败**：
   - **红队**（`pnpm redteam`）：模型编写对抗用例，真实 agent 运行，规则加评审打分（评审还能看到系统的工具调用结果）；
   - **PM 纠正**（`pnpm eval:harvest`）。

   两者都会变成*草稿*场景，由人审核。

改进闭环：

```
生产 / 红队 ─► 草稿场景 ─► 人工审核 ─► eval 套件 ─► 改提示词 / 策略 / 模型 ─► CI + eval
```

本项目的例子：红队第二轮找到了三个真实问题：
- agent 声称"已安排"，但实际上并没有安排；
- 租客说"先别派人"之后，agent 仍然继续推进；
- 升级摘要写着"已回复租客"，实际什么都没发。

每个问题都已修复，并保留为回归场景。

## 9. 可观测性与成本

- **追踪**：每次模型调用一个 OpenTelemetry GenAI span（模型、token、延迟、步骤），导出到 Langfuse；每个工单还有工作流 span。
- **错误**：Sentry，在服务端上报，个人信息已脱敏。
- **业务审计**：只追加的 `audit_log`，PM 可以按工单和案件查看。
- **成本**：每次调用都记入 `llm_calls`（以百万分之一美元为单位，含缓存 token）。后台显示每个工单的成本。有每日预算和模拟器限流，
  每个步骤组可以用不同的模型（比如写消息用更便宜的模型）。实测：Claude Opus 5.5 每个场景 0.06 美元、19.5 秒。
- **健康检查**：有待执行的迁移时，`/api/v1/health` 返回失败。

## 10. 多租户与数据

- 每张带 `organization_id` 的表都有 RLS 策略，缺了会有测试失败。
- 请求范围内的访问通过 `withOrg()` 以受限角色运行；后台 worker 有意使用 owner 角色，但每个查询都按公司过滤。
- 媒体有保留期（180 天，每天清理）；金额用纽币整数分；时间以 UTC 存储，按 Pacific/Auckland 显示。

## 11. 模型选择、成本与数据出境

- 一个 `LlmClient` 接口。默认 Claude，OpenAI 兼容的服务商走适配器。
- 可以按物业公司（`organizations.llm_routing`）或按部署（`LLM_DEFAULT_MODEL`、`LLM_STEP_MODELS`、`LLM_VISION_MODEL`、`LLM_FALLBACK_MODEL`）路由，按步骤组划分：`triage`、`retriage`、`act`、`interpret`、`compose`、`vision`、`route`、`ops`。
- **按 eval 分数和成本选模型，而不是凭偏好。** 目前的对比：Claude Opus 5.5 抽样集 15/15，每个场景 0.06 美元（4.1 次调用）；Kimi K2.6 全量修复前 54/60，速度慢约 4 倍。

### 11.1 经济账：便宜的模型实际能省多少

一个完整的维修工单大约 10 次模型调用。按抽样集的单价，用 Claude Opus 大约 0.10–0.20 美元。这是根据 eval 运行估算的，不是生产环境实测。和物业经理手工处理一个工单的成本相比，模型费用不到工单价值的 1%。

代价高的失败在别处：

| 失败 | 谁来买单 |
|---|---|
| 错误的升级（Kimi 的升级准确率是 88%，Claude 是 100%） | 每次都浪费 PM 的时间 |
| 漏掉的升级 | 安全事故和责任 |
| 回复太慢（Kimi 的 compose p95 是 100 秒） | 报紧急情况的租客要等 |

所以在主流程上，省 token 带来的损失比省下的钱更多。值得做的节省，是把简单的步骤交给**同一家服务商**的小模型（`interpret` 和 `compose` 用 Claude Haiku 5.5，按标价每个 token 便宜 40 倍），并且要先通过 eval。
调用量很大时（每月几十万次），钱主要省在这种按步骤拆分、提示词缓存和第 1 层规则上。

### 11.2 数据出境决定了便宜的境外模型能用在哪里

新西兰 Privacy Act（IPP 12）规定，个人信息发往境外，必须有可比的保护措施，或者取得本人的知情同意。严格说，所有托管模型对新西兰来说都在境外，包括 Claude（美国）。
区别在于保护措施：物业公司和他们的律师可以接受的数据处理协议和数据保留限制。把租客的姓名、地址、家里的照片发给没有这些保护措施的服务商，不管多便宜，对物业公司和房东来说都是信任问题。

所以每个步骤组都有一个**数据级别**（`src/agent/providers/registry.ts` 里的 `STEP_DATA_CLASS`），路由配置会按它校验：

| 数据级别 | 步骤 | 没有保护措施的境外服务商（DeepSeek、Kimi） |
|---|---|---|
| `personal`：姓名、地址、消息、照片 | `triage`、`retriage`、`act`、`interpret`、`compose`、`vision`、`route` | **拒绝**，无论是作为路由模型还是作为备用模型。只有设置了 `syntheticDataOnly`（只含虚构数据的部署：开发、演示）才允许 |
| `aggregate`：只有计数和数字 | `ops`（运营分析师） | 开启境外同意项后允许 |
| 合成数据，不经过路由 | eval、红队的生成和评审 | 在种子数据上用固定的 `--model` |

配置错误时默认拒绝：路由解析失败，工单的模型客户端建不起来，工单带着原因升级，绝不会悄悄把个人信息发到境外。

**便宜模型适合的地方：** 红队生成、eval 模拟和 CI（合成数据）；运营分析师（汇总数字）；基于公开房源信息写招租文案、回答咨询（做出来之后）；开发。
**规模变大后：** Kimi 是开源权重模型，可以部署在澳大利亚区域或自己的基础设施上，数据不出境，单价也低。等每月调用量大到差价有实际意义时，值得评估。

## 12. 框架：LangGraph、DeerFlow 等——为什么这里不用

| 方案 | 提供什么 | 是否适合本项目 |
|---|---|---|
| **LangGraph** | 基于图的编排、检查点状态、用 `interrupt()` 等待人工输入、流式输出、LangSmith 追踪和评测 | 没用。这里的流程是固定的业务流程；状态应该在业务表里；等好几天、定时器和重试属于持久化执行的问题（Inngest）。再加一个检查点存储会变成第二个依据。迁移接口：任何图节点都可以调用 `executeTool`，审计、权限和幂等都不受影响 |
| **DeerFlow**（字节跳动） | 基于 LangGraph 的多 agent 深度研究框架：规划者、研究员、程序员、报告员；联网搜索、执行代码 | 形态不对。它是为开放式研究和报告生成设计的；这里是事务型系统，模型主导的规划和代码执行正是要避免的风险。可以用来做只提供建议的*研究型*功能（租金可比数据、投诉趋势） |
| OpenAI Agents SDK、Claude Agent SDK、CrewAI、AutoGen、Mastra、Pydantic AI | agent 循环、交接、工具注册 | 取舍相同；这里那个精简的循环只有几十行，完全可控 |
| Temporal、Step Functions | 持久化执行 | 与 Inngest 等价；需要自托管时可以考虑（[`architecture.zh-CN.md`](architecture.zh-CN.md) 第 4 节） |
| MCP | 把工具暴露给任何 agent 的标准方式 | 很好的下一步：把工具网关做成 MCP server，让其他 agent（或 Keyhook 自己的）在同样的权限和审计下使用 |

### 12.1 为什么不用通用的 agent harness

*harness* 是模型外面的所有东西：循环、工具、上下文和记忆、权限、子 agent、上下文压缩。Claude Code、Claude Agent SDK、OpenAI Agents SDK 都是通用 harness。它们是为路径未知的开放式工作（写代码、做调研）设计的，由模型决定下一步做什么。

| 通用 harness 的假设 | 这个业务需要的 |
|---|---|
| 模型选择下一步 | 下一步遵循业务和法律规则，由状态机决定 |
| 一个会话在一个进程里跑完 | 一个工单持续好几天，靠事件唤醒，部署后还要能接着跑（Inngest） |
| 权限 = 人在终端里点“允许” | 权限 = 存在库里的 PM 审批记录、金额限额、每家公司的策略 |
| 记忆 = 对话历史，再加压缩 | 记忆 = Postgres 里的业务状态，每一步重新构建 |
| 探索式循环，调用次数不固定 | 每个场景约 4 次调用，成本和延迟可以预测 |
| 单个用户 | 多家物业公司：RLS、审计、隔离 |

这个项目其实也有 harness，只是它很窄、按业务定制：

| harness 的部件 | 项目里对应的是 |
|---|---|
| 工具网关 | `executeTool`：权限、幂等、审计 |
| 模型层 | `RoutingLlm`：按步骤路由、超时、熔断、故障切换 |
| 循环 | 状态机 + Inngest |
| 上下文 | 每一步从数据库重建 |
| 反馈 | eval、红队、运营分析师 |

这就是 “harness engineering” 在实践中的含义：模型周围的环境，比由哪个框架提供循环更重要。

**通用 harness 适合的地方：** 没有固定路径的开放式任务。编码 agent 就是 Claude Code，它本身就是一个 harness。以后的事故分诊 agent（读日志和代码、复现问题、提出修复）适合放在沙箱里用 Claude Agent SDK 来做。
原则是：**固定流程跑在状态机上，开放式任务跑在 harness 上。** 两者可以共用同一个工具网关。

**什么时候值得用框架：**
- 有很多 agent，并且它们怎么协作要在运行时决定；
- 团队统一使用那套生态；
- 需要图级别的回放和调试。

无论用不用框架，护栏都应该留在本代码库里：状态机的权威、审批记录、幂等、审计和 RLS。

## 13. 下一个 agent 的检查清单

在这个平台上做一个新 agent，满足以下各项才算"完成"：

- [ ] 代码里的状态机，有终止状态，并且只有 PM 能让案件离开升级状态；
- [ ] 工具都通过 `executeTool`：Zod schema、权限级别、幂等键；不可撤回的动作用 approval 级工具；
- [ ] 处理器遵循提取 → 代码决策 → 撰写，不可信输入要包裹，注入要升级；
- [ ] 升级材料包包含摘要、已做的事、建议和证据；
- [ ] 持久化的触发方式（事件、定时任务），按对象控制并发；
- [ ] 新表都有 RLS，查询都按公司隔离；
- [ ] 用脚本化模型写数据库测试，写 eval 场景（包括注入和"应该升级"的情况），并为红队加一个关注类别；
- [ ] 一条决策记录（中英文），并加入 agent 目录。

欠租（M9）正是按这份清单做的：一个状态机、五个工具、一个策略函数、九个场景。

## 14. 生产级 agent 的常见关注点：哪些做了，哪些还没做

下面是生产级 agent 常见的检查项，以及本项目的对应情况。✅ = 已实现并有测试，◐ = 部分实现，✗ = 还没有（附计划）。

| 关注点 | 状态 | 做法 |
|---|---|---|
| **任务规划 / 子任务** | ✅ | 没有自由发挥的规划器。状态机本身就是计划：每个状态是一个有处理函数的子任务，模型只在一步之内做决定（§1）。一条消息里报了需要不同工种的多个问题时，会升级给 PM 拆分。不同 agent 之间的交接走收件箱路由。 |
| **工具的输入和输出** | ◐ | 输入：每个工具有 Zod schema，`executeTool` 在执行前校验；有权限级别、幂等键和审计记录。输出在代码里有类型，但返回给模型前没有做 schema 校验。待补：输出也要校验。 |
| **参数边界** | ✅ | 金额是整数分，上限来自策略；时间段 id 必须是提供过的选项；师傅 id 必须来自 `search_tradies`；需要审批的工具在没有已存的审批记录时拒绝执行。 |
| **工具并发和调用频率** | ✅ | 同一个工单 / 欠租案件同一时间只有一个运行（Inngest 并发键）；每个 act 步骤最多 8 轮工具调用；幂等保证重试安全。 |
| **记忆** | ◐ | 短期：每一步都从 Postgres 重新构建工单上下文（工单、房屋、租客、最近 12 条消息、这个房屋过去的工单）。长期：数据库本身（工单历史、Portfolio Monitor 发现、PM 的纠正）。没有向量记忆——这里没有需要语义检索的地方。待补：长对话做摘要，而不是只保留最近 12 条。 |
| **幻觉兜底** | ✅ | 模型负责提取，代码负责决定（§1）。结构化输出做 schema 校验；金额由代码解析；模型不能编造状态、师傅或时间段。输出不可用 → 升级给 PM。 |
| **超时** | ✅ | 按步骤设置请求超时，数值来自实测延迟（`src/agent/timeouts.ts`）；SDK 重试一次，之后由 Inngest 持久化地重试这一步。 |
| **限流** | ◐ | 模拟器：每个物业公司每小时的消息数上限和每日 LLM 预算；访客登录：每个 IP 每小时 20 次。待补：按服务商的令牌桶，让突发的大量工单排队，而不是收到 429。 |
| **降级 / 故障切换** | ✅ | `LLM_FALLBACK_MODEL` 加每个模型一个熔断器（60 秒内失败 3 次 → 跳过 60 秒）。永久性错误（认证、余额）带着原因升级给 PM，而不是悄悄失败。熔断状态保存在单个进程内；共享存储的版本在路线图里。 |
| **全量调用留痕** | ✅ | 每个工单都有 `llm_calls`（步骤、模型、输入/输出/缓存 token、费用、耗时、停止原因、错误）和 `audit_log`（每次工具调用、状态变化和规则决策），在工单页以“Agent 调用轨迹”展示；OpenTelemetry span 发到 Langfuse。 |
| **用量分析** | ✅ | `/dashboard/usage` 按步骤和模型汇总调用；由代码检测出发现（超时风险、失败、没用上的缓存、换便宜模型能省多少、规则候选）；每周的运营分析师 agent 负责排序，不能自己添加发现。任何改动仍然要先跑 eval。 |
| **省钱、省 token** | ✅ | 先用规则再用模型（见下）；对稳定前缀做提示词缓存（缓存命中在调用轨迹里能看到）；按步骤路由，简单步骤用便宜的模型；每一步单独设置 effort；每日预算。 |
| **意图识别漏斗** | ◐ | 第 1 层，规则：固定的短回复（选时间、简单确认）不进模型。第 2 层，状态：工单当前的状态已经决定了回复可能的含义，所以不需要开放式的意图分类——收件箱路由（是欠租还是维修？）只在有未结欠租案件的租客发来一条还没关联到工单的消息时才运行。第 3 层，模型：处理其余所有情况。待补：只在 eval 数据证明安全的地方增加第 1 层规则。 |
