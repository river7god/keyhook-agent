# 示例项目：用一个电商客服 Agent 串起所有技术

> **为什么要另举例子？** Keyhook 刻意没用 LangGraph、RAG、Skills 等技术。为了面试时能讲清这些技术，这里虚构一个项目 **ShopAssist**，每个技术只回答三件事：**是什么 · 用在哪 · 为什么**。
> 数字都是假设，用来说明取舍。

---

## 1. 项目是什么

**ShopAssist**：一家卖电子产品的电商公司的 AI 客服。

- **顾客**：问产品、查订单、退换货
- **人工客服**：只接 AI 搞不定的
- **主管**：批大额退款
- **运营**：想知道"退货率为什么涨了"

规模：每天 5 万条咨询，2000 件商品，几百页政策和说明书。目标：70% 由 AI 闭环解决。

---

## 2. 架构（从上到下）

```
渠道（网站 · App · 微信）
   ↓
对话层   LangGraph：路由 Agent → 售前 / 订单 / 售后 Agent → 转人工
   ↓ 需要等几天的事（退货）
流程层   Temporal：等寄回 → 质检 → 退款
   ↓
工具层   MCP Servers（订单 · 物流 · 支付）+ 权限 / 幂等 / 审计网关
知识层   RAG：pgvector + 关键词检索 + 重排序
记忆层   用户画像 + 对话摘要
模型层   LLM 网关：路由 · 缓存 · 降级 · 预算

旁路：运营分析 Agent（Agent SDK + Skills + 沙箱）
      供应商门户 Agent（Computer Use）
      物流公司 Agent（A2A）
```

---

## 3. 一个请求走一遍

顾客：**"上周买的耳机左边没声音了，能退吗？"**

| 步 | 发生什么 | 技术 |
|---|---|---|
| 1 | 检查有没有注入，遮掉手机号 | 护栏、脱敏 |
| 2 | 判断意图 = 退货，交给售后 Agent | 多 Agent、微调小模型 |
| 3 | 读到这是 VIP，喜欢换货 | 长期记忆 |
| 4 | 查订单：7 天前签收，¥899 | 工具调用、MCP |
| 5 | 查政策：15 天内质量问题可退 | RAG |
| 6 | ¥899 > 自动上限 ¥500 → 暂停等主管 | 人在回路 |
| 7 | 主管批准 → 从断点继续 | LangGraph checkpoint |
| 8 | 启动退货流程，等 7 天寄回 → 退款 | Temporal、幂等 |
| 9 | 全程记录每次调用 | 追踪、审计 |

## 4. 每个技术一句话

### 模型层
| 技术 | 是什么 | 这里怎么用 | 为什么 |
|---|---|---|---|
| **LLM 网关** | 所有模型调用的统一入口 | 简单任务用小模型，难的用大模型；挂了切备用 | 统一控成本和故障 |
| **Prompt 缓存** | 固定的开头部分缓存起来 | 系统提示词 + 工具定义 | 省钱、更快 |
| **结构化输出** | 要求模型按 JSON 格式回答 | `{intent, confidence}`，校验失败转人工 | 代码才能可靠地用结果 |
| **微调** | 用自己的数据再训练模型 | 只用于意图分类（30 类、几十万条标注） | 高频固定任务才值得 |

> 口诀：**知识用 RAG，行为用 prompt，高频固定才微调。**

### 编排层
| 技术 | 是什么 | 这里怎么用 | 为什么 |
|---|---|---|---|
| **LangGraph** | 把流程画成图来跑，每步自动存档 | 路由 → 专家 Agent → 输出 | 对话开放，顾客会中途换话题 |
| **多 Agent** | 一个总调度 + 多个专家 | 路由 + 售前 / 订单 / 售后 | 每个专家更专、工具更少 |
| **Temporal** | 能等几天、保证做完的流程引擎 | 退货：等寄回 7 天 → 质检 → 退款 | 服务器会重启，流程不能丢 |

LangGraph 的 5 个词：**State**（共享状态）· **Node**（一步）· **条件边**（下一步去哪）· **Checkpointer**（存档）· **interrupt**（暂停等人）。

> 口诀：**LangGraph 管"这段对话怎么聊"，Temporal 管"这件事几天后办完"。**

### 工具层
| 技术 | 是什么 | 这里怎么用 | 为什么 |
|---|---|---|---|
| **Tool calling** | 模型说"调哪个工具"，代码执行 | 查订单、建退货单、退款 | 模型只提议，代码执行 |
| **三级权限** | read / auto / approval | ¥500 以下自动退；以上要审批，模型看不到这个工具 | 防越权 |
| **MCP** | 连接工具的标准协议（AI 的 USB-C） | 订单、物流、支付各一个 MCP Server | 多个 Agent 共用一套工具 |
| **按需加载** | 每个 Agent 只给需要的工具 | 60 个工具，订单 Agent 只看 8 个 | 工具太多模型会选错 |

> 注意：**MCP 只管"怎么接"，权限和审计要自己的网关做。**

### 知识层
| 技术 | 是什么 | 这里怎么用 | 为什么 |
|---|---|---|---|
| **RAG** | 先检索资料，再让模型回答 | 政策、说明书、历史工单 | 资料多、常更新，塞不进上下文 |
| **切块 + 向量** | 文档切成小段，转成向量存起来 | 约 500 token 一段，存 pgvector | 按意思搜 |
| **混合检索** | 向量搜（意思）+ 关键词搜（字面） | 型号"WH-1000XM5"必须精确匹配 | 向量搜不准型号 |
| **重排序** | 再用一个模型挑最相关的 | 50 条里挑 5 条 | 更准 |
| **Agentic RAG** | 检索变成 Agent 的工具，自己决定搜几次 | 搜政策、搜说明书、搜工单 | 复杂问题要多次搜 |

> 口诀：**资料少直接放上下文；多、常变、要过滤才用 RAG。**

### 记忆
| 类型 | 存什么 | 存在哪 |
|---|---|---|
| 短期 | 这次对话 | LangGraph checkpoint |
| 长期 | 会员等级、偏好、历史摘要 | Postgres |
| 语义 | 类似问题以前怎么解决 | pgvector |

对话太长 → 把早期内容压缩成摘要（Compaction）。

### 运营分析 Agent（开放式任务）
运营问"上个月退货率为什么涨了？"，Agent 自己查数据、写代码分析、出报告。

| 技术 | 是什么 | 这里怎么用 |
|---|---|---|
| **Agent SDK / Harness** | 现成的 Agent 运行框架（Claude Code 同款） | 自己决定查什么、算什么 |
| **沙箱** | 隔离环境跑 AI 写的代码 | 无网络、只读账号、有时间上限 |
| **子 Agent** | 派出去干子任务，只带回结论 | 三个类目并行分析 |
| **Hooks** | 动作前后自动检查 | 执行 SQL 前禁止 DELETE/UPDATE |
| **Skills** | 一份操作手册，用到才加载 | 周报格式、退货率分析方法 |

> 口诀：**Tool 是螺丝刀，Skill 是说明书，MCP 是插座。**

### 对外连接
| 技术 | 是什么 | 这里怎么用 |
|---|---|---|
| **A2A** | Agent 和 Agent 之间的协议 | 和物流公司的 Agent 约取件 |
| **Computer Use** | 模型看截图、点鼠标 | 操作没有 API 的供应商老网站；提交前给人确认 |

> 口诀：**MCP 连工具，A2A 连 Agent。**

### 安全、评测、运维
| 方面 | 做法 |
|---|---|
| **注入** | 顾客消息当数据；检索来的内容也不可信（间接注入） |
| **隐私** | 输入脱敏；只能查当前顾客的订单 |
| **幻觉** | 回答必须带政策原文引用；找不到就转人工 |
| **人在回路** | 短时间等用 `interrupt`；跨天的用审批记录表 |
| **评测** | 单元测试 → RAG 评测（搜得准吗）→ 500 个场景 → AI 评委 → 红队 → 线上 5% A/B |
| **可观测** | 每段对话一条 trace（Langfuse）；看解决率、转人工率、成本 |
| **发布** | Prompt 放 git、改动过评测；先 5% 流量再全量 |

## 5. 和 Keyhook 对比（面试最有价值）

| 技术 | ShopAssist | Keyhook | 原因 |
|---|---|---|---|
| LangGraph | 用 | 不用 | 对话开放 vs 流程固定 |
| 等几天的流程 | Temporal | Inngest | 都需要，选哪个看团队 |
| RAG | 用 | 不用 | 大量文档 vs 结构化数据（SQL 就够） |
| MCP | 用 | 计划中 | 多个 Agent 共用工具 vs 单一代码库 |
| Skills / Agent SDK | 用 | 不用 | 开放任务 vs 固定流程 |
| 微调 | 用 | 不用 | 每天 5 万次 vs 量小 |
| A2A / Computer Use | 用 | 不用 | 有没有外部 Agent、老系统 |
| 权限 · 幂等 · 审计 · 护栏 · 评测 · 人在回路 | 用 | 用 | **任何生产级 Agent 都必须有** |

> 一句话：**架构看场景选，安全和质量的底线永远要有。**

## 6. 系统设计题 8 步（"设计一个 XX Agent"）

1. **问清需求**：谁用、做什么、哪些涉及钱和安全、多大规模
2. **划人机边界**：可逆吗、影响大吗、有把握吗、谁负责
3. **选编排**：固定 → 状态机；开放 → LangGraph / Agent SDK；要等几天 → Temporal / Inngest
4. **设计工具**：权限分级 + 幂等 + 审计；要共用就 MCP
5. **知识**：结构化 → SQL；文档多 → RAG；文档少 → 直接放上下文
6. **安全**：注入、隐私、越权、幻觉
7. **评测**：离线场景 + 红队 + 线上 A/B
8. **运维**：追踪、成本、降级、灰度发布

> **30 秒总结**："我先划人机边界，再按任务选架构：固定流程用状态机，开放对话用 LangGraph，跨天流程用 Temporal 或 Inngest；文档多用 RAG，结构化数据用 SQL。无论哪种，权限、幂等、审计、护栏、评测、人在回路都必须有。Keyhook 就是这样选了状态机 + Inngest，没用 LangGraph 和 RAG。"
