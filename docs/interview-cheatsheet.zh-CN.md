# 第一部分：速记

## 1. 一句话 + 一个金句（必背）

- **项目一句话**：租客报修，AI 从第一条消息一路处理到关单；只有需要判断或授权时才找物业经理。
- **核心金句**：**"模型负责抽取和撰写，代码负责决策。"**
- **定位**：这是**事务型** agent（钱、安全、别人的家），所以可靠性放在代码里。

## 3. 必背数字

| 数字 | 含义 |
|---|---|
| **12** | 工单状态数（终态：CLOSED、CANCELLED） |
| **≤ 8 轮** | 唯一的工具循环（只在 TRIAGED 状态），之后自检 |

| **0.7** | 分诊置信度阈值，低于就升级 |
| **12 条** | 每步上下文带最近 12 条消息 |
| **84** | 评测场景数；冒烟集 **17** 个约 **1 美元** |
| **290+** | 代码测试数 |
| **0** | 禁止动作必须为 0（硬红线） |
| **约 0.06 美元 / 约 4 次调用** | 每个评测场景的成本和调用次数；完整工单约 10 次调用 |
| **0.88 vs 1.0** | Kimi vs Claude 的升级精确率 |
| **30 秒** | 升级包让经理 30 秒内做决定 |
| **5% 或 NZ$50** | 发票核对容差 |

## 4. 架构五层（从上到下）

```
app（鉴权、RLS）→ workflows（Inngest：事件、重试、并发 1）→ agent（抽决写）
→ tools（校权幂审）→ domain/db（唯一入口、组织隔离、只追加审计）
```

## 5. 工单流程（一口气说完）

```
报修 → 分诊（紧急/低置信/注入/法律 → 升级；缺信息 → 追问）
→ 找师傅要报价 → [等几天，没回就催]
→ 报价按"自·批·升"处理 → 约时间（"选 2"走规则，不调模型）
→ 上门 → 租客确认 → 关单（通知业主、核对发票）
任意状态 → 升级（经理接手，只能交还原状态）/ 取消（只有经理）
```

## 6. 各主题一句话

**Agent 设计**
- Workflow vs Agent：谁决定下一步——代码还是模型。本项目是 workflow + 一个有界工具循环。
- 记忆：每步从数据库重建上下文，不是聊天记录；没用向量库，因为不需要语义回忆。
- 意图漏斗：规则 → 状态 → 模型，最便宜且正确的一层先上。

**可靠性**
- 幂等：key 和副作用在同一事务，重试返回上次结果。"至少一次投递 + 幂等 = 效果上恰好一次。"
- 乐观锁：`version` 列；先认领再执行；数据库是真相，事件丢了下次扫描补回。
- 失败：拒答/乱码/配置错误 → 立即升级，不盲目重试；工单绝不默默卡住。

**安全**
- 注入：`<untrusted_message>` 包裹 + 注入标志 → 升级且不发任何消息；图片里的字也一样。
- 最好的防护：让模型**被骗了也做不了危险的事**（审批工具对模型不可见）。
- 多租户：每行 `organization_id` + Postgres RLS，数据库强制隔离，缺策略测试就失败。
- 数据驻留：每步有数据分级，个人数据不发给无保障的境外模型，配错即拒绝。

**扩展技术**
- RAG：先检索再回答；质量主要看检索（切块、混合检索、重排序）。
- RAG 过时了吗：过时的是一刀切的向量流水线，不是检索；现在是 Agentic RAG。
- 向量库：中小规模选 pgvector，能沿用事务和 RLS。
- LangGraph vs Temporal：LangGraph 管"这次对话怎么聊"，Temporal 管"几天后要办完"。
- Skill：渐进式披露，平时只占一行简介，用到才加载。
- Harness：模型是引擎，harness 是整辆车。
- MCP vs A2A：MCP 是 agent 接工具，A2A 是 agent 之间协作。
- 微调：知识用 RAG，行为用 prompt，高频固定且有大量数据才微调。

**CI/CD**
- 两件事：用 agent 做 CI/CD + 给 AI 应用做 CI/CD（LLMOps）。
- 护栏：写审分离 · 确定性检查优先 · 最小权限 · 沙箱 · agent 不能改自己的护栏 · fork PR 不给密钥。
- 风险分级 A/B/C：文档自动合并 → 普通代码一人批 → 数据库/权限/prompt/CI 两人批。

## 7. 选型判断（最体现水平）

| 因场景而异 | 永远必须有 |
|---|---|
| 编排框架、RAG、微调、Skills、A2A、Computer Use | 权限分级、幂等、审计、护栏、评测、人在回路、可观测 |

> "固定流程用状态机；开放对话用 LangGraph；跨天用持久化执行；知识多且变用 RAG，结构化数据用 SQL。"

# 第二部分：面试题库（遮住答案自测）

## A. 项目介绍类

**1. 介绍一下你的项目。**
> 新西兰物业维修 AI agent，租客报修后从分诊、找师傅、报价审批、约时间、追催到确认关单全自动，只在需要判断或授权时找经理。因为涉及钱和安全，决策放在代码里——状态机、工具网关、Inngest——AI 只负责理解和撰写。有 84 个评测场景，禁止动作保持为 0。

**2. 这个项目解决了什么业务问题？**
> 一个维修工单牵涉 4 个人、3 个系统、约 9 个手工步骤。AI 做协调，经理从"干活"变成"监督"，一个经理能管更多物业。

**3. 为什么叫"事务型" agent？有什么不同？**
> 它的动作有真实后果：花钱、派人上门、法律通知。所以不能让模型自由发挥，关键决策必须可预测、可审计、可回滚。

## B. 架构与 Agent 设计类

**4. 系统架构是怎样的？**
> 模块化单体，五层：app（鉴权 + RLS）→ workflows（Inngest）→ agent（每个状态一个 handler）→ tools（统一网关）→ domain/db（唯一数据入口）。不用微服务，因为一个团队，接口就是将来拆分的接缝。

**5. LLM 在系统里做什么，不做什么？**
> 做：理解消息（结构化抽取）、看照片、写回复、在一个有界循环里选师傅。不做：决定下一个状态、算钱、判断是否升级——这些由代码做。

**6. 状态机怎么保证 AI 不乱跳步？**
> 状态转换写在代码里，每次写入都过 `checkTransition`。模型只能看到当前允许的转换菜单，它说的不算。还有乐观锁防止并发冲突。

**7. 唯一的工具循环在哪？怎么约束？**
> 只在 TRIAGED 状态，模型自己选工具找师傅、要报价。最多 8 轮，结束后代码自检"状态真的变了吗"，没变就升级。

**8. Agent 的记忆怎么做？**
> 每步从数据库重建上下文：工单、物业、租约、最近 12 条消息、历史工单。长期记忆就是数据库本身。没用向量库，因为数据都是结构化的。

**9. 为什么不用 LangGraph？**
> 固久一：流程固定，状态机就够；要等好几天，是持久化执行问题，用 Inngest；状态只放业务表，一个真相来源。如果是开放式任务我会考虑它。

**10. 一个工单要等几天，怎么实现？**
> 状态存数据库，程序不常驻。Inngest 用事件唤醒；追催行每 5 分钟扫描一次，先认领再执行；失败重试 3 次后升级；同一工单并发为 1。

## C. 可靠性类

**11. 重试时怎么保证不重复发短信？**
> 幂等 key = 工单版本 + 触发消息 + 工具名 + 调用序号，和副作用在同一个事务保存点里。重放返回上次的结果；同 key 不同请求直接报错。

**12. 两条消息同时到同一个工单怎么办？**
> Inngest 并发键 = 工单 ID，串行处理；入站消息最多处理一次，第二次会被检测并中止。

**13. 模型返回乱码或拒答怎么办？**
> 结构化输出 + Zod 校验，失败抛 `LlmOutputError`/`LlmRefusalError`，立即升级给经理并附原因，不盲目重试——换个模型也解决不了内容问题。

**14. 模型供应商挂了怎么办？**
> 每步有超时；有备用模型；熔断器 60 秒内失败 3 次就跳过 60 秒。永久错误（鉴权、余额）直接升级。紧急情况一定能到人。

**15. 为什么不在数据库事务里调 LLM？**
> LLM 慢，会长时间占用连接和锁。先做完 LLM 调用，再在一个短事务里落所有副作用。

## D. 安全类

**16. 怎么防 prompt 注入？**
> 外部消息用 `<untrusted_message>` 包裹并中和闭合标签；抽取结果有注入标志，命中就升级、不发任何消息；图片里的文字同样处理。更重要的是模型本来就够不到危险工具。

**17. 怎么防止 AI 乱花钱？**
> 钱由代码用整数分计算；超额必须有数据库里的审批记录；批钱的工具对模型不可见。

**18. 多租户怎么隔离？**
> 每行有 `organization_id`，复合外键；Postgres RLS，每个请求事务里切到受限角色；任何表缺 RLS 策略，测试就失败。

**19. 审计怎么做？**
> 每次工具调用和状态转换写一行审计（谁、什么、为什么、输入、输出、trace id），表是只追加的，数据库触发器拒绝修改。

**20. 隐私和数据出境？**
> 每个步骤有数据分级；含个人信息的步骤不能发给无保障的境外模型（新西兰隐私法 IPP 12）；配置错了直接拒绝并升级；Sentry 发送前脱敏。

## E. 评测与质量类

**21. 怎么知道 AI 做得好不好？**
> 假·真·红：假 AI 测代码逻辑（每次提交）；84 个场景用真模型跑（每晚，禁止动作为 0）；红队和经理纠错找没想到的问题，人审后进题库。

**22. 评测场景长什么样？**
> 一个 YAML：输入（租客说"厨房有煤气味"）+ 期望（紧急、升级、禁止要报价）。跑完打分。

**23. 评测发现过什么真问题？**
> 红队发现 agent 谎称"已安排好"、租客说"先别派人"仍继续、升级摘要说"已回复租客"其实没发。改成只根据事实清单撰写，并保留为回归场景。

**24. 为什么要检查升级的"原因"而不只是结果？**
> 结果对、原因错是潜在 bug，换个输入就会出错。

**25. LLM-as-judge 可靠吗？**
> 需要明确评分标准和人工抽查校准。本项目的评委还能看到系统的工具执行结果，不只看文字。

## F. 模型与成本类

**26. 怎么选模型？**
> 看评测分数和成本，不凭偏好。每个步骤可以用不同模型。例如 Kimi 的升级精确率 0.88，Claude 是 1.0——每次错误升级都耗经理时间，便宜 token 可能很贵。

**27. 怎么省钱？**
> 规则优先（固定短回复不调模型）、prompt 缓存稳定前缀、简单步骤用同厂商的小模型（评测通过后）、每日预算、每次调用记录成本。

**28. 一个工单成本多少？**
> 评测中每个场景约 0.06 美元、4 次调用；完整工单约 10 次调用，约 0.1–0.2 美元，远低于人工处理成本。

## G. 扩展知识类

**29. 什么是 RAG？什么时候用？**
> 先检索相关资料再让模型回答，解决模型不知道私有或最新知识。资料多、常更新、要权限过滤时用。本项目数据是结构化的，SQL 更准，所以没用。

**30. 有人说 RAG 过时了，你怎么看？**
> 过时的是一刀切的向量流水线。资料少就放进上下文加缓存；资料多仍然要检索，而且越来越多让 agent 把检索当工具用（Agentic RAG）。

**31. 向量库怎么选？**
> 中小规模首选 pgvector，和业务数据在一起，能用事务和 RLS；上亿向量、高 QPS 才考虑专用向量库。

**32. Tool、Skill、MCP 的区别？**
> 刀·册·口：Tool 是能力，Skill 是方法和经验（渐进式披露），MCP 是连接工具的标准协议。三者互补。

**33. 什么是 Agent Harness？**
> 模型之外的一切：循环、工具、上下文管理、记忆文件、子 agent、hooks、权限、沙箱。同一个模型，harness 好坏效果差很多。

**34. MCP 和 A2A 的区别？**
> MCP 是 agent 接工具，A2A 是 agent 之间协作。

**35. 什么时候微调？**
> 先 prompt，缺知识加 RAG，只有高频、固定、有大量数据的任务才微调。知识用 RAG，行为用微调。

**36. LangGraph 和 Temporal 能一起用吗？**
> 能。LangGraph 管对话内的编排（秒到小时），Temporal 管跨天的业务流程。业务状态放数据库，checkpoint 只存对话上下文。

## H. CI/CD 类

**37. 你在 CI/CD 里怎么用 AI？**
> 每个 PR 由两个独立的审查 agent（审查 + 安全审查）给建议；按改动路径自动分 A/B/C 风险等级；确定性检查才能阻止合并，人做决定。另外 prompt/模型改动要过评测。

**38. 会让 AI 自动合并代码吗？**
> 按风险分级。低风险（文档、测试）在数据证明可靠后可以；数据库、权限、prompt、CI 永远要人，而且 agent 不能改自己的护栏。

**39. 为什么写代码和审代码要用不同的 agent？**
> 同一上下文有同样的盲点。我们第一次跑审查，46 秒、0.33 美元，就抓到了作者漏掉的"永远不会失败的测试"。

**40. 怎么防止 CI 里的 agent 被攻击？**
> PR/issue 内容当不可信输入；fork PR 拿不到密钥、不用 `pull_request_target`；最小权限 token；编码 agent 在沙箱里跑。

## I. 系统设计与开放类

**41. 让你设计一个电商客服 agent，你会怎么做？**
> 按 8 步：澄清需求 → 划人机边界 → 选编排（开放对话用 LangGraph，跨天退货用 Temporal）→ 设计工具（权限 + 幂等 + MCP）→ 知识（政策和说明书用 RAG + 混合检索）→ 安全（直接和间接注入）→ 评测（场景 + RAG 评测 + 红队 + A/B）→ 运维。→ 示例项目文档

**42. 你的项目有什么不足？下一步做什么？**
> 工具输出没校验；长对话只保留最近 12 条，应该做摘要；限流缺按供应商的令牌桶；熔断器状态是单进程的；生产迁移和 Inngest 同步还是手动的。下一步：发布流水线自动化、评测变成 PR 门禁、工具做成 MCP server。

**43. 如果规模扩大 100 倍？**
> 沿接缝拆分：先拆消息网关，再拆 LLM 网关，再拆媒体服务；大表按月分区；读写分离；需要数据驻留时迁到 AWS 新西兰区域。每次迁移要有触发条件，不因为大公司这么做就做。

**44. 你做过最重要的技术决策是什么？**
> 让代码决策、模型只抽取和撰写。这让系统可测试、可审计，成本可预测，也让我能放心地用便宜模型做简单步骤。

## 30 秒自我介绍

> "我做了一个物业维修的 AI agent，能把租客的报修从第一条消息一路处理到关单。因为涉及钱和安全，我把**决策放在代码里**——状态机管流程、工具网关管权限/幂等/审计、Inngest 管长时间等待——**AI 只负责理解和撰写**。我还建了 84 个评测场景和红队测试，保证'不该做的事'始终为 0，并在 CI 里用两个独立的 AI 审查 agent 审每个 PR。"

## 别这么说 ❌ → 这么说 ✅

| ❌ | ✅ |
|---|---|
| "AI 决定要不要退款/派人" | "AI 抽取信息，代码按规则决定" |
| "RAG 已经过时了" | "一刀切的向量流水线在退场，检索变成了 agent 的工具" |
| "LangGraph 不好" | "LangGraph 适合开放式编排，我的场景是固定流程" |
| "我们的 AI 很准" | "升级精确率 1.0、禁止动作 0，在 84 个场景上测的" |
| "用了很多框架" | "每个技术解决什么问题，为什么用或不用" |
| "AI 审查代码，所以不需要人" | "确定性检查阻止合并，AI 给建议，人做决定" |

## 万能答题框架

被问任何技术：**解决什么问题 → 怎么工作 → 代价 → 我为什么用/不用 → 什么情况会改变选择**
